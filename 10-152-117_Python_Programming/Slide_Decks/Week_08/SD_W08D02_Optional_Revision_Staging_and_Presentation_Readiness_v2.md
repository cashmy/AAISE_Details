make the final result stronger.

## Slide 3 - Reality Contact Reveals Priorities

**Delivery Category:** Optional

**Student-Visible Text:**

Running the project may reveal:

- a feature is too large
- a data format is harder than expected
- an output needs to be clearer
- a smaller core is the better final version

**Instructor Notes:**

This is a concise version of the older Day 2 lecture.

## Slide 4 - Refactoring Should Improve Coherence

**Delivery Category:** Optional

**Student-Visible Text:**

Refactoring should make the project easier to read, run, test, or explain.

Cosmetic changes are fine, but coherence matters more.

**Instructor Notes:**

Keep it practical. Do not start a broad refactoring lecture.

## Slide 5 - Record One Meaningful Revision

**Delivery Category:** Optional

**Student-Visible Text:**

Before final submission, record one meaningful revision:

- what changed
- why it changed
- how the project became stronger or more realistic

**Instructor Notes:**

This supports A16 explanation.

---

## Slide 6 - Presentation Is Explanation

**Delivery Category:** Optional

**Student-Visible Text:**

Your final presentation should explain:

- what you built
- what problem or purpose it addresses
- how the main logic works
- how you tested or validated it
- what changed during the project
- how AI was used, if applicable

**Instructor Notes:**

This can be used as the short pre-presentation reset.

---

## Slide 7 - AI Use Must Be Accounted For

**Delivery Category:** Optional

**Student-Visible Text:**

If AI helped, explain:

- what AI contributed
- what you accepted
- what you changed or rejected
- how you verified the result
- what decisions remained yours

**Instructor Notes:**

Keep it non-accusatory and accountability-focused.
