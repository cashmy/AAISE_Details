# Session Purpose

This session turns framing into proposal readiness.

Students should revise their A13 framing into a realistic capstone proposal that
can be reviewed, approved, or redirected. The emphasis is not on defending every
original feature. The emphasis is on creating a project that can be finished,
tested, explained, and owned.

**Delivery Category:** Core

**Student-Visible Text:**

A smaller clear project usually beats a larger vague project.

The capstone is not judged by how many features you imagine. It is judged by
whether the project can run, be tested, and be explained.

## Slide 6 - Constraints Are Part Of The Design

**Delivery Category:** Core

**Student-Visible Text:**

Constraints include:

- time
- skill level
- data access
- explainability
- testing difficulty
- course fit

Good constraints make the project stronger by making reality visible.

**Instructor Notes:**

This line matters: constraints are not insults to ambition.

---

## Slide 7 - Feature Count Is Not Project Quality

**Delivery Category:** Core

**Student-Visible Text:**

More features can make a project weaker if they make it harder to finish or
explain.

Capstone quality comes from a coherent working core.

**Instructor Notes:**

Use this repeatedly during proposal conferences.

---

## Slide 8 - Scope Reduction Is A Professional Move

**Delivery Category:** Core

**Student-Visible Text:**

Scope reduction asks:

- What is the core useful behavior?
- What can be removed?
- What can become a future feature?
- What must remain explainable?

**Instructor Notes:**

Connect to Agile/MVP thinking without overloading the slide.

---

## Slide 9 - Structure Should Match The Project

**Delivery Category:** Core

**Student-Visible Text:**

Possible structures:

- one clear script
- function-based program
- file/data utility
- API-style program
- simple class-based structure, if justified

The structure should serve the project, not decorate it.

**Instructor Notes:**

This avoids prestige bias around classes/APIs.

---

## Slide 10 - Risks Should Be Named Before Coding

**Delivery Category:** Core

**Student-Visible Text:**

Risks are things that could make the project harder:

- live API instability
- unclear data format
- too many features
- logic not yet understood
- AI code the student cannot explain

Naming risk early makes revision easier.

**Instructor Notes:**

This is a major A14 quality marker.

# AI-Use Boundary

Manual first:

- propose the project idea
- identify the core useful behavior
- decide what must be explainable

AI may help later with:

- identifying risks
- suggesting feature cuts
- comparing project structures

AI must not choose the final project or expand scope beyond approval.
