# Session Purpose

This session introduces RBA as a practical project-framing process.

The day is not about writing more Python syntax. It is about deciding what the
project is supposed to accomplish before asking AI, copying patterns, or writing
major code.

Students should leave with a concrete framing artifact that can feed directly
into their capstone proposal.

---

## Slide 6 - Purpose Comes First

**Delivery Category:** Core

**Student-Visible Text:**

The project purpose answers:

- What problem or need does this address?
- Who uses it?
- What would count as a useful result?

If the purpose is vague, everything after it becomes harder to judge.

**Instructor Notes:**

Push students toward concrete use, not vague themes.

**Transition Cue:**

Once the purpose is clear, define what the program receives and produces.

---

## Slide 7 - Inputs And Outputs Define The Shape

**Delivery Category:** Core

**Student-Visible Text:**

Inputs are what the program receives.

Outputs are what the program produces.

Clear inputs and outputs make the project easier to build, test, and explain.

**Instructor Notes:**

Connect back to every assignment. Inputs/outputs have been present all course.

**Transition Cue:**

After inputs and outputs, use constraints to make the project realistic instead
of merely ambitious.

---

## Slide 8 - Constraints Are Design Information

**Delivery Category:** Core

**Student-Visible Text:**

Constraints are not just obstacles.

Time, skill level, data availability, explainability, and course scope all help
shape a realistic project.

**Instructor Notes:**

Normalize constraints as helpful. This sets up Day 2 scope control.

**Transition Cue:**

The structure should then follow the purpose and constraints, not prestige or
habit.

---

## Slide 9 - Structure Should Fit The Intent

**Delivery Category:** Core

**Student-Visible Text:**

Possible project structures include:

- API-style fetcher
- light architecture-preview project, if approved

The structure should fit the purpose.

**Instructor Notes:**

Do not let prestige bias make advanced paths look automatically better.

**Transition Cue:**

Before AI enters the work, define what the student still owns.

# AI-Use Boundary

Manual first:

- define the first version of the project idea yourself
- write the initial purpose and constraints
- decide what AI should not choose

AI may help later with:

- identifying missing risks
- comparing structure options
- tightening scope language

AI must not choose the project purpose or replace student judgment.
