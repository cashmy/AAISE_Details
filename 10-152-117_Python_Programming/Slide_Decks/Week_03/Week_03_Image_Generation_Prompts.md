# Week 3 Image Generation Prompts

**10-152-117 Python Programming**

---

# Purpose

This companion artifact expands the Week 3 v2 deck source image notes into
explicit image-generation prompts.

Use these prompts when PowerPoint Designer does not provide a useful visual or
when a slide needs a precise instructional diagram.

---

# Style Guidance For All Week 3 Images

Use a clean educational diagram style for beginner programming students.

Preferred visual qualities:

- light background
- simple vector-style diagrams
- readable labels
- one main idea per image
- limited color palette
- minimal code
- no dense screenshots
- no intimidating technical imagery

Avoid:

- complex architecture diagrams
- professional DevOps pipelines
- database diagrams unless explicitly requested
- robot or AI imagery unless the prompt asks for AI accountability
- overly abstract shapes that do not teach the slide concept
- cluttered flowcharts

# Week 3 Day 1 - Naming Responsibility With Functions

Source deck:

`SD_W03D01_Naming_Responsibility_with_Functions_v2.md`

## Slide 1 - Code Can Work And Still Be Messy

Create a clean split visual. Left side: one long undivided Python-like code
block labeled "working but hard to scan". Right side: the same idea divided
into three named sections labeled "calculate", "decide", and "show". Use a
calm instructional style and make the right side visibly easier to follow.

Avoid shaming rough code, red error marks, or dense real code.

## Slide 2 - Flow Becomes Shape

Create a visual showing Week 2 concepts flowing into functions. Use small cards
labeled variables, conditions, and loops, with arrows leading into a function
box labeled "named responsibility". The image should communicate that functions
organize skills students already learned.

Avoid implying functions replace conditions or loops.

## Slide 3 - Today's Success Pattern

Create a four-step visual: repeated logic, named responsibility, function call,
clearer program. Use arrows between each step. The "named responsibility" step
should be emphasized with a label card.

Avoid abstract architecture diagrams.

## Slide 4 - What We Will Use Today

Create a toolbox visual with labeled cards for `def`, function names, function
calls, parameters, return values, and small refactors. Use a simple classroom
diagram style with readable labels.

Avoid recursion, lambdas, decorators, or advanced function topics.

## Slide 5 - What We Will Skip For Now

Create a calm "parked for later" shelf with four labeled cards: recursion,
lambdas, decorators, and advanced imports. Add a small bookmark or clock icon
to show these are useful later but not today's focus.

Avoid warning signs or making the deferred topics look wrong.

## Slide 6 - Repeated Code Is A Signal

Create a visual showing two short repeated code-like blocks with matching lines
highlighted. Add a label: "same job repeated". The image should suggest that
repetition is a clue to inspect for a possible function.

Avoid full code walls or unreadable text.

## Slide 8 - A Function Owns One Clear Job

Create a single function card labeled `calculate_total` with one job label:
"calculate total with tax". Show one small input arrow and one output arrow.
The image should emphasize one clear responsibility.

Avoid showing multiple unrelated jobs inside the same function.

## Slide 9 - Function Shape

Create a minimal instructional diagram distinguishing a function definition
from a function call. Left side: `def calculate_total(price):` labeled
"definition". Right side: `calculate_total(12.00)` labeled "call". Use a simple
arrow from call to definition.

Avoid long code examples.

## Slide 10 - Demo 2: Refactor Into A Function

Create a before/after visual. Before: repeated tax calculation shown as three
similar blocks. After: one function card named `calculate_total` called three
times. Emphasize less repetition and clearer responsibility.

Avoid too much numeric detail.

## Slide 11 - Values Come In, Results Come Out

Create a simple box-and-arrow diagram: input value -> function box -> returned
result. Label the input arrow "parameter" and the output arrow "return value".
Keep the diagram spacious and beginner-friendly.

Avoid abstract math notation.

## Slide 12 - Demo 3: Input, Process, Output Responsibilities

Create three function boxes in a row: `calculate_average`, `get_status`, and
`show_result`. Add small labels under each: calculate, decide, display. Use
arrows to show a simple program flow.

Avoid implying a full enterprise architecture.

## Slide 13 - Common Failure: More Functions Is Not Better

Create a split visual. Left side: two or three meaningful function cards with
clear labels. Right side: many tiny unlabeled fragments scattered around.
Caption the left side "intentional" and the right side "too fragmented".

Avoid making the right side comedic or insulting.

## Slide 15 - Assignment 4 Bridge

Create a small beginner program transforming into two named function cards.
The cards should be labeled `calculate_total` and `show_result`. Include a
short caption: "Name the jobs before adding more code."

Avoid large applications or many function cards.

## Slide 17 - Evidence For A Function Program

Create a lightweight evidence visual showing one `.py` file, two function
cards, a small output sample, and a short explanation note. Keep the layout
organized and simple.

Avoid heavy documentation imagery.

# Week 3 Day 2 - Storing Related Data With Lists And Dictionaries

Source deck:

`SD_W03D02_Storing_Related_Data_with_Lists_and_Dictionaries_v2.md`

## Slide 1 - Programs Become Useful When They Remember Things

Create a clean visual of several related values grouped into a small Python
program. Use example values such as tasks, scores, or course details. Show the
program producing useful output from the grouped values.

Avoid database cylinders for this slide; keep it about beginner in-memory data.

## Slide 2 - Logic Uses Data

Create a diagram with a function box using a list or dictionary card, then
producing output. Label the pieces "logic", "related data", and "visible
result". Keep the image simple.

Avoid architecture or database diagrams.

## Slide 3 - Today's Success Pattern

Create a four-step horizontal flow: store related data, retrieve useful values,
loop or look up, show output. Use simple icons or cards for each step.

Avoid complex branching.

## Slide 4 - What We Will Use Today

Create a toolbox visual with cards labeled list, index, append, loop,
dictionary, key, value, and lookup. Use readable text and simple icon-like
cards.

Avoid comprehensions, generators, databases, or APIs.

## Slide 5 - What We Will Skip For Now

Create a "parked for later" shelf with cards labeled comprehensions,
generators, advanced collections, databases, and complex nested data. Add a
small caption: "Useful later, not today's focus."

Avoid warning visuals or suggesting the topics are bad.

## Slide 6 - Lists Keep Related Items Together

Create an instructional visual of a Python list containing three task cards:
read, practice, submit. Show square brackets around the group and label it
"one list variable".

Avoid too many list items.

## Slide 7 - List Positions Start At Zero

Create a list visual with three items labeled index 0, index 1, and index 2.
Highlight index 0 and label it "first item". Make zero-based indexing visually
clear.

Avoid detailed explanations of memory or arrays.

## Slide 8 - Demo 1: List Basics

Create a before/after list visual. Before: three tasks in a list. After:
`append()` adds a fourth task. Include a small loop output panel listing each
task on its own line.

Avoid code-heavy layout.

## Slide 10 - Dictionaries Connect Meaning To Value

Create a dictionary visual as labeled key/value pairs. Use keys such as
`number`, `title`, and `credits`, each connected to its value. Make the key
labels look like meaningful names.

Avoid making it look like a database table.

## Slide 11 - Keys Are Not Positions

Create a clear split comparison. Left side: list access with a numeric position
such as `tasks[0]`. Right side: dictionary access with a meaningful key such as
`course["title"]`. Label the left "position" and the right "key".

Avoid too many examples.

## Slide 12 - Demo 2: Dictionary Lookup

Create a visual where `course["title"]` points to the value "Python
Programming". Also show `course["credits"]` pointing to `2`. Use arrows from
lookup expressions to values.

Avoid full dictionaries with many keys.

## Slide 13 - Choosing A Structure

Create two side-by-side panels. Left panel: "Use a list when order or looping
matters" with task cards. Right panel: "Use a dictionary when labels matter"
with key/value cards.

Avoid making one structure look better than the other.

## Slide 14 - Demo 3: List Of Dictionaries

Create three record cards inside a larger list container. Each record card
should have two labels: name and score. Show a loop arrow moving through one
record at a time.

Frame this as a bridge to future structured data, not a requirement for every
student.

## Slide 15 - Assignment 5 Bridge

Create small mini-app option cards: task list, simple inventory, score tracker,
and course lookup. Each card should show a data structure leading to visible
output.

Avoid making one option appear required.

## Slide 17 - Evidence For A Data Mini-App

Create a lightweight evidence layout showing one `.py` file, a list or
dictionary card, a small output sample, and a short structure-choice note.

Avoid large documentation imagery.

# Week 3 Day 3 - Comparing Rough And Cleaner Program Structure

Source deck:

`SD_W03D03_Comparing_Rough_and_Cleaner_Program_Structure_v2.md`

## Slide 1 - Working Code Can Still Improve

Create a split visual. Left side: rough working code with repeated or crowded
parts. Right side: cleaner organized code with named functions and grouped
data. Both sides should appear functional, but the right side should be easier
to scan.

Avoid making rough code look like broken code.

## Slide 2 - Functions Plus Data Structures

Create a diagram showing function boxes working with data structure cards.
Labels should include "named jobs", "related data", and "visible output". Keep
the diagram beginner-level.

Avoid enterprise architecture or database diagrams.

## Slide 3 - Today's Success Pattern

Create a four-step revision flow: working baseline, compare structure, revise
one meaningful thing, explain improvement. Use arrows and simple labeled cards.

Avoid heavy project-management imagery.

## Slide 4 - What We Will Use Today

Create a toolbox visual with cards labeled rough baseline, cleaner version,
function responsibility, data choice, comparison questions, and small revision.

Avoid architecture jargon.

## Slide 5 - What We Will Skip For Now

Create a "parked for later" shelf with cards labeled broad redesign,
class-based architecture, large AI rewrites, and project restructuring. Add a
caption: "Save these until the current structure is clear."

Avoid warning visuals or robot-takeover imagery.

## Slide 6 - Correct Is Not The Same As Clear

Create two balanced cards. One card: "Correct" with expected output. Other
card: "Clear" with readable structure and explanation. Show that both are
important with equal visual weight.

Avoid implying correctness is optional.

## Slide 7 - Cleaner Structure Is Easier To Explain

Create a visual with clear function names and grouped data leading to a speech
bubble labeled "I can explain this." Use small code-like labels, not full code.

Avoid dense code.

## Slide 8 - Comparison Questions

Create five question cards: What changed? Why does it help? What became easier?
What stayed the same? What would I change next? Arrange them as a simple review
checklist.

Avoid cluttered sticky-note walls.

## Slide 9 - Demo: Rough vs Organized Structure

Create an annotated comparison visual. Left side: rough version with repeated
output formatting. Right side: organized version using a function card named
`format_task`. Highlight "repetition reduced" and "job named".

Avoid including the entire demo code.

## Slide 11 - What Got Easier?

Create five simple cards or icons labeled read, test, change, reuse, and
explain. Use a clean layout showing that improvement should make at least one
of these easier.

Avoid generic productivity dashboards.

## Slide 12 - Manual Baseline Comes First

Create an ordered flow diagram: manual baseline -> human comparison -> optional
AI critique -> human decision. Make "manual baseline" the first and most
important step.

Avoid showing AI as the starting point.

## Slide 13 - AI Suggestions Are Not Automatic Answers

Create a diagram showing an AI suggestion card passing through a human decision
filter. The output should be labeled "accepted", "changed", or "rejected".
Keep the human decision visually central.

Avoid robot imagery that suggests AI is in control.

## Slide 14 - Finish A4: Function Builder

Create two or three function cards with responsibility labels. Include a small
checklist: names, calls, responsibilities, explanation.

Avoid large function libraries.

## Slide 15 - Finish A5: List Or Dictionary Mini-App

Create a data mini-app visual showing a list or dictionary card feeding visible
output. Include a small label: "structure choice explained".

Avoid database or API imagery.

## Slide 17 - Evidence For Week 3

Create an evidence layout with `.py` files, a function explanation note, a data
structure choice note, and a small output sample. Keep it neat and
student-friendly.

Avoid capstone or portfolio imagery.
