# RELEASE STRATEGY FOR PYTHON COURSE ARTIFACTS

**10-152-117 Python Programming**

---

# Purpose

This artifact defines a practical release strategy for the Python course artifacts.

The goal is **not** to slow production.

The goal is to control publication in a way that is:

* believable
* reviewable
* strategically paced
* flexible for continued refinement

This release strategy assumes that artifact creation is moving faster than typical institutional expectations and that publication should therefore be staged intentionally.

---

# Guiding Principle

The distinction that matters is:

* **produced**
* versus
* **published**

The course ecosystem may be produced faster than it is publicly released.

That is a strategic choice, not a contradiction.

---

# Current Status Assumptions

The following are already posted or materially in place:

* Master Rubric System
* Standard Student AI-Use Policy and addenda
* Schoology scaffolding structure using Unit / Week descriptions

The following exist but are **not** assumed to require publication at this time:

* IIM
* APL
* alignment artifacts
* meta-reviews
* process / governance artifacts

These are treated primarily as:

* design support artifacts
* instructor governance artifacts
* refraction / revision artifacts

unless a later audience-specific version is created.

---

# Recommended Release Model

Use a combined strategy:

* **artifact-family release**
* with a **small weekly-course proof slice**

In practice:

* fully release Week 1 as the complete exemplar package
* then release the balance of the course in staged artifact-family blocks

This gives reviewers and supervisors:

* one concrete complete instructional package
* visible evidence of quality and coherence
* a believable ongoing release cadence

while still preserving:

* revision flexibility
* time for support-book work
* time for future companion materials

---

# Release Logic

## Why Week 1 Should Be Fully Visible

Week 1 should act as the public proof-of-pattern.

It demonstrates:

* the instructional standard
* the document stack
* the student experience model
* the connection between assignments, demos, lecture outlines, and decks

This is far easier for others to understand than a statement that "the whole course exists."

It gives them something inspectable.

---

## Why the Remaining Course Should Be Dripped

The remaining weeks should be staged because this:

* keeps the release believable
* avoids overwhelming review capacity
* preserves time for refinement
* allows additional support artifacts to be created in parallel
* prevents unusually high output from being misunderstood as implausible

The goal is not concealment.

The goal is controlled release.

---

# Recommended Publication Categories

## Category A - Public / Ready for Instructional Use

These are appropriate to publish early or steadily:

* Week 1 full package
* assignment artifacts
* lecture outlines
* slide-deck markdown artifacts
* student-facing policies and instructions
* approved resource wrappers

---

## Category B - Internal / Instructor-Governance

These should generally remain unpublished unless specifically needed:

* IIM
* APL
* Assignment Week / Day Matrix
* Lecture Content and Demo Alignment Matrix
* meta-review artifacts
* process artifacts
* heuristic comparison artifacts

These are better understood as:

* internal instructional architecture

rather than student- or admin-facing documents.

---

## Category B2 - Instructional Support Assets (Shown by Default, Published Optionally)

These are normally used as:

* live teaching assets
* demonstration assets
* instructor reference assets

Examples:

* demos
* success examples

Important distinction:

these assets are typically **shown** in instruction before they are necessarily **published** to students.

Their publication channel should remain flexible.

Possible future publication paths include:

* no direct publication, instructor-show only
* timed-release Schoology pages
* a GitHub repository

At this stage, the better stance is:

* keep them available for teaching use
* delay publication-channel commitment until live class behavior reveals what is actually most helpful

---

## Category C - Audience-Specific Future Artifacts

If other stakeholders later need visibility, create targeted artifacts rather than exposing raw governance artifacts.

Possible examples:

* supervisor summary
* faculty overview
* program-level innovation brief
* AI-assisted course-design case summary

This preserves clarity and audience fit.

---

# Recommended Release Waves

## Wave 1 - Already Released / Foundational

Includes:

* Master Rubric System
* Student AI-use policy / addenda
* Schoology week structure scaffolding

Purpose:

* establish foundational course infrastructure

---

## Wave 2 - Full Week 1 Exemplar

Release the complete Week 1 instructional package.

Recommended contents:

* Week 1 assignments
* Week 1 demos
* Week 1 success examples
* Week 1 lecture outlines
* Week 1 slide decks
* any Week 1 student-facing support material

Purpose:

* demonstrate the full instructional pattern in one inspectable slice

Why this matters:

* it makes the course design tangible
* it proves coherence without forcing the entire course into immediate visibility

---

## Wave 3 - Core Student Task Layer

Release the remaining assignment artifacts in staged blocks.

Recommended grouping:

* Weeks 2-4 assignments
* Weeks 5-6 assignments
* Weeks 7-8 assignments

Purpose:

* make the student performance layer visible in a believable progression

---

## Wave 4 - Demo and Success Layer

Prepare demos and success examples in corresponding blocks for instructional use.

Recommended grouping:

* Weeks 2-4 demos and success examples
* Weeks 5-6 demos and success examples
* Weeks 7-8 support/demo materials as appropriate

Purpose:

* ensure the instructional support structure exists and is ready for use without forcing immediate publication

Publication note:

these materials may be:

* shown only
* timed-released in Schoology
* later organized into a GitHub repository

The final publication mode should remain dependent on observed class engagement and instructional need.

---

## Wave 5 - Lecture and Slide Layer

Release lecture outlines and slide-deck markdown artifacts in blocks.

Recommended grouping:

* Weeks 2-4 lecture / slide materials
* Weeks 5-6 lecture / slide materials
* Weeks 7-8 lecture / slide materials

Purpose:

* complete the visible instructional system in paced releases

---

# Optional Timing Pattern

If a weekly supervisor cadence is being used, a believable release rhythm could be:

* meeting cycle 1: Week 1 full package
* meeting cycle 2: Weeks 2-4 assignments and selected demos
* meeting cycle 3: Weeks 2-4 lecture / slide materials plus Weeks 5-6 assignments
* meeting cycle 4: Weeks 5-6 demos / lecture / slide materials
* meeting cycle 5: Weeks 7-8 instructional materials

This is only a pattern example.

The actual pace should remain flexible.

---

# Strategic Benefits

This release strategy preserves:

* credibility of output volume
* review absorbability
* time for continued refinement
* flexibility for support-book development
* space for additional instructor aids and companion materials
* flexibility in deciding whether code examples should be shown, published, or both

It also reduces a common risk:

* a complete internal ecosystem being mistaken for something that must all be externally visible at once

---

# What Should Be Said Verbally Instead of Documented

This strategy assumes that some contextual explanation will be given verbally rather than through a separate formal note.

Examples:

* what has already been produced internally
* what is being staged intentionally
* what remains unpublished because it is governance-oriented
* what additional companion materials may still be created

This is appropriate when the verbal relationship already exists and does not require a separate explanatory memo.

---

# Final Recommendation

Use:

* **Week 1 as the complete public proof-of-pattern**

then continue with:

* **staged artifact-family release in believable blocks**

while keeping:

* governance artifacts internal

unless a later audience-specific version is intentionally crafted.

This approach preserves both:

* the reality of accelerated production
* and the institutional believability of the release cadence

That makes it the strongest practical release strategy for the current moment.
