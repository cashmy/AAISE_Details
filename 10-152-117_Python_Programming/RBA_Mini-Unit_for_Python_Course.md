# RBA Mini-Unit for Python Course

---

# Purpose

This artifact defines a compressed, bounded introduction to Refraction-Based Architecture (RBA) for use inside `10-152-117 Python Programming`.

The intent is not to make RBA the invisible default methodology of the entire Python course.

The intent is to:

* introduce students to an emerging AI-era development paradigm
* distinguish it clearly from traditional development workflows
* connect it to project development in a bounded, intelligible way
* preserve portability so students can still operate in conventional environments
* create a foundation that can be referenced again in later courses

This mini-unit assumes Python remains the primary course subject and RBA remains a distinct, explicitly framed development-methodology layer.

---

# Instructional Position

RBA should be taught in this course as:

* an emerging development framework
* a human-governed way of structuring AI participation
* a distinct paradigm rather than an industry default
* a process the instructor uses in real project development
* a bounded introduction rather than full mastery

RBA should not be taught here as:

* the only correct way to build software
* a replacement for learning Python fundamentals
* a substitute for debugging, testing, or code comprehension
* a claim about how most traditional shops currently operate

---

# Why Keep It Compressed

A compressed RBA mini-unit is preferable to a fully diffused RBA presence across the course because:

* RBA is still very new and not yet widely normalized
* students should understand that it differs from common shop expectations
* category clarity matters: Python fundamentals and RBA are related but not identical
* a distinct introduction makes later cross-course reference easier
* a bounded treatment reduces the risk that students misread RBA as the universal industry workflow

This approach allows the course to preserve:

* conventional beginner Python development habits early
* anti-cheating and manual-first learning patterns
* explicit contrast between standard workflows and RBA
* future reuse if the framework becomes a recurring program-level method or OER text

---

# Recommended Placement in the Course

The mini-unit should occur after students have already developed enough Python fluency to understand project structure, debugging, and simple application development.

Recommended placement:

* late Week 5 through Week 6
* or Week 6 through early Week 7

This timing works because students will already have encountered:

* variables and control flow
* functions and data structures
* debugging and testing
* file and data handling

That gives them enough technical footing to understand RBA as a project-development process rather than as abstract philosophy.

---

# Recommended Length

Recommended scope: `2-3 sessions`

This is enough time to:

* introduce the framework
* compare it with more conventional development approaches
* apply it in a bounded project-planning or project-refactoring context

This is not enough time for:

* full theoretical treatment
* exhaustive terminology
* full architectural depth

That is appropriate for this course.

---

# Student-Facing Learning Goal

After this mini-unit, students should be able to say:

> "I understand that RBA is a newer way of developing AI-assisted systems in which the human defines intent and structure before using AI for implementation support. I can describe the main idea, compare it with more conventional workflows, and apply it in a small project setting."

---

# Core Ideas Students Should Understand

## 1. Human Intent Comes First

Before building, the human defines:

* what the system is for
* what problem it is solving
* what must be preserved
* what constraints matter

Students should understand that RBA does not begin with:

* "ask AI to generate something useful"

It begins with:

* "define the purpose and boundaries first"

---

## 2. Structure Before AI Participation

Students should understand that in RBA, AI is introduced after the work has been framed.

At a beginner-friendly level, this means deciding things such as:

* what the program should do
* what inputs and outputs exist
* whether the solution is a script, a multi-function program, or a small class-based structure
* what the success criteria are

---

## 3. AI Is a Refraction Medium, Not the Source of Meaning

Students should understand that AI can help transform intent into code or options, but AI does not decide:

* the purpose of the project
* the governing criteria
* whether the result is acceptable

This is one of the most important distinctions in the mini-unit.

---

## 4. Development Is Top-Down, but Not Rigidly Linear

Students should understand that RBA is not just:

* plan once
* build once
* finish

Instead, the process can move downward into implementation and then back upward when:

* code drifts from purpose
* the structure is weak
* the result exposes new constraints
* reality reveals something that the earlier framing missed

This should be presented in plain language rather than heavy formalism.

---

## 5. Reality Contact Matters

Students should understand that building a working artifact quickly is valuable because real constraints appear when something is runnable.

This is not the same as rushing blindly.

The idea is:

* frame clearly
* build quickly enough to reach reality
* learn from what the artifact reveals
* revise intentionally

---

## 6. Explanation and Validation Remain Human Responsibilities

Students should understand that even if AI helps produce code, the student is still responsible for:

* testing it
* checking whether it meets the intent
* explaining what it does
* deciding what should be kept, revised, or rejected

---

# What Students Do Not Need in This Course

Students do not need:

* full formal mastery of the RBA framework
* deep terminology memorization
* philosophical precision about every layer and principle
* proof that RBA is universally accepted in industry

The course should aim for:

* conceptual recognition
* bounded practical application
* contrastive understanding

---

# Recommended Student Language

The student-facing language should remain practical and accessible.

Preferred classroom wording:

* define the purpose first
* decide the structure before asking for code
* treat AI output as a draft
* test what you build
* revise when reality shows a problem
* explain your choices

Use formal RBA terminology selectively:

* `RBA`
* `intent`
* `structure`
* `descent`
* `refinement`

Use `SKY`, `CORE`, `BASE`, and `SkyFall` only if they materially help the lesson. They should not become vocabulary overhead in a beginner Python course.

---

# Recommended Session Structure

## Session 1 — What RBA Is and Why It Differs

### Main Goal

Introduce RBA as a distinct development paradigm and compare it with conventional bottom-up or ad hoc AI use.

### Core Topics

* why faster code generation is not the same as coherent development
* human intent before implementation
* architecture or structure before AI participation
* AI as transformation medium, not originator
* contrast with conventional prompting-first behavior

### Suggested Activities

* compare two development starts:
* "prompt first"
* "intent and structure first"
* analyze a small example of code generated with weak framing versus code generated with stronger framing
* discuss how a traditional shop might view the process differently

### Student Outcome

Students can describe the central difference between ad hoc AI use and RBA.

---

## Session 2 — RBA as a Project Development Process

### Main Goal

Show how RBA functions during project formation and early implementation.

### Core Topics

* define purpose, boundaries, and success criteria
* choose a simple program shape
* descend into implementation
* move back upward when friction appears
* refactor and refine

### Suggested Activities

* take a small Python project idea and frame it before coding
* identify inputs, outputs, constraints, and likely structure
* compare a procedural option and a class-based option
* review a generated draft and decide what should be changed

### Student Outcome

Students can apply a simplified RBA flow to a small Python project.

---

## Session 3 — Bounded Application to Capstone or Mini-Project

### Main Goal

Use RBA in a constrained way during project work without presenting it as the only valid professional workflow.

### Core Topics

* use RBA to frame the project
* validate code against purpose
* refactor for coherence
* explain where AI helped and where human judgment was needed
* distinguish between this paradigm and more conventional shop expectations

### Suggested Activities

* complete a short project framing sheet
* generate or revise part of a project under explicit constraints
* present how the project changed after reality contact
* reflect on where this process might align or conflict with other environments

### Student Outcome

Students can use RBA in a bounded way and explain both its strengths and its limits.

---

# Contrast With Traditional Development

This mini-unit should explicitly address difference rather than assume compatibility.

Students should hear clearly that RBA may differ from:

* bottom-up coding habits
* task-first prompting
* conventional Agile interpretations
* shop norms built around tickets, frameworks, or implementation-first expectations

The point is not to dismiss those environments.

The point is to help students understand that:

* RBA is a different governing posture
* different environments may expect different workflows
* professional maturity includes recognizing which model is active in a given context

---

# Misconceptions to Prevent

## Misconception 1 — "RBA means AI does the hard part"

Correction:

RBA increases the importance of human judgment, framing, and validation.

---

## Misconception 2 — "RBA replaces Python fundamentals"

Correction:

Students still need enough Python fluency to read, test, debug, and explain solutions.

---

## Misconception 3 — "RBA is just better prompting"

Correction:

Prompting is downstream of the architectural posture.

---

## Misconception 4 — "This is how all companies now build software"

Correction:

RBA is emerging and may not align with many traditional shops.

---

## Misconception 5 — "If the code works once, the process succeeded"

Correction:

Success includes coherence, explainability, validation, and preserved intent.

---

# Capstone Relationship

RBA should inform the capstone in a bounded way.

Recommended expectation:

* students should be able to frame a project using simplified RBA ideas
* students may use AI support inside that structure
* students should explain how intent shaped implementation choices
* students should describe at least one revision caused by testing, friction, or reality contact

RBA should not require students to:

* produce a full formal architecture document
* use the complete terminology stack
* pretend this is the only legitimate project method

---

# Assessment Implications

If assessed in this course, RBA should be assessed lightly and interpretively.

Appropriate assessment targets:

* can the student define project intent clearly
* can the student identify structure before generation
* can the student explain what AI contributed and what the human decided
* can the student describe a revision after testing or friction
* can the student compare RBA with a more conventional workflow at a basic level

Inappropriate assessment targets for this course:

* formal mastery of all RBA principles
* advanced architectural theory
* complete operational fluency with the full framework

---

# Recommended Instructor Framing

A useful framing statement might be:

> "Later in this course, we will look at an emerging development framework called Refraction-Based Architecture. This is part of my own process for developing AI-assisted projects. It is not the universal industry default, and it is not a replacement for Python fundamentals. In this class, you will learn what it is, how it differs from more conventional workflows, and how to apply it in a bounded project setting."

---

# Most Important Outcome

Students should leave this mini-unit understanding that RBA is a distinct, human-governed approach to AI-assisted project development, not simply a permission slip to generate code faster.
