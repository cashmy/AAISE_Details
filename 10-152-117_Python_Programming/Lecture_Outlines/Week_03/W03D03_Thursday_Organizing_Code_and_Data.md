> "Today we are not asking only whether the code works. We are also asking whether the organization helps a human understand and manage the program."

Suggested wording:

> "This week has been about shaping code and shaping data. Today we compare structure choices so students can begin recognizing what improvement actually looks like."

# 5. Core Concepts (10-20 minutes)

## Concept 1 - Working code is not always well organized code

Plain-language explanation:

* a program can run and still be difficult to read or revise

Why it matters:

* students need to value readability before later AI comparison work becomes meaningful

## Concept 2 - Cleaner structure improves explainability

Plain-language explanation:

* named functions and organized data make a program easier to talk through

Why it matters:

* explanation is part of the course, not an extra layer

## Concept 3 - Comparison teaches judgment

Plain-language explanation:

* looking at two versions helps students develop better design instincts

Why it matters:

* the course is preparing students to compare manual work with AI-generated alternatives later

## Concept 4 - AI comparison comes after manual baseline

Plain-language explanation:

* AI should not be the first move here
* students must first build enough understanding to judge the comparison

Why it matters:

* this protects learning and keeps AI use bounded

Students should:

* finish Function Builder work
* finish the collection mini-app
* compare one rough version with one cleaner version

Suggested wording:

> "Your goal today is not to make your code fancy. Your goal is to make it more understandable than it was before."

Use this session for:

* revision
* cleanup
* naming improvements
* explanation practice

---

# 8. Common Mistakes / Watch-Fors (5-8 minutes)

## Mistake 1 - assuming cleaner means longer or more complex

Why it happens:

* students may equate sophistication with improvement

Correction:

* show that cleaner often means simpler and more intentional

## Mistake 2 - AI comparison happens before manual understanding

Why it happens:

* students may want the comparison before they have enough judgment

Correction:

* require a manual baseline first

## Mistake 3 - changes are made, but the student cannot explain why they are better

Why it happens:

* students may revise by imitation rather than judgment

Correction:

* ask them to justify the organizational improvement directly

---

# 9. Explain / Checkpoint Questions (3-8 minutes)

Ask:

* What is clearer in the revised version?
* What repeated code was reduced?
* How is the data easier to manage now?
* Why is this version easier to explain than the earlier one?

---

# 10. End-of-Class Success Check

> By the end of this session, students should be able to compare a rough program to a cleaner version and explain what organizational changes made the code easier to understand.
