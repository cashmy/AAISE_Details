# Remote Paired Programming Lecture Deck Source

**Reusable Bonus Recording**  
**Audience:** Beginning programming, web development, and algorithms students  
**Working Title:** Paired Programming - How To Work Together Remotely

---

# Session Purpose

This bonus lecture explains how students should work together remotely in Zoom
on labs and assignments.

Paired programming is not intended for capstone ownership. It is a structured
way to learn, practice, and complete assigned collaborative work while keeping
both students mentally active.

# Slide-By-Slide Source

### Slide 1 - Paired Programming Is Structured Collaboration

Student-visible text:

```text
Paired Programming

How to work together remotely.

The goal:

- shared understanding
- better problem solving
- fewer silent mistakes
- both students able to explain the work
```

**Instructor notes:**

- State that this applies to paired/group labs and assignments, not individual
  capstone ownership unless specifically allowed.

**Transition cue:**

- "Pairing is more than one person watching another person type."

### Slide 2 - What Paired Programming Is

Student-visible text:

```text
Paired programming means:

- two people work on one problem
- one person drives
- one person navigates
- both talk through decisions
- both understand the result

It is a learning strategy, not just a faster way to finish.
```

**Instructor notes:**

- Emphasize shared cognition and communication.

**Transition cue:**

- "It helps to name what pairing is not."

### Slide 3 - What Paired Programming Is Not

Student-visible text:

```text
Paired programming is not:

- one person doing all the work
- one person silently watching
- splitting the assignment with no review
- copying code no one understands
- letting AI replace the conversation
```

**Instructor notes:**

- This slide addresses the common failure modes directly.

**Transition cue:**

- "The basic two-person structure is driver and navigator."

### Slide 4 - Driver And Navigator

Student-visible text:

```text
Driver:

- shares screen
- controls keyboard
- types the current change
- says what they are doing

Navigator:

- reads requirements
- watches logic
- asks questions
- checks the next step
```

**Instructor notes:**

- The navigator is active, not passive.
- Encourage students to speak frequently.

**Transition cue:**

- "Groups of three need one more role."

### Slide 5 - Groups Of Three

Student-visible text:

```text
For groups of three:

Driver:
types and shares screen.

Navigator:
guides the coding step.

Checker:
watches requirements, tests, and notes questions.

Rotate roles every 10-15 minutes.
```

**Instructor notes:**

- The checker prevents the third person from becoming invisible.

**Transition cue:**

- "Remote pairing needs a clean Zoom setup."

### Slide 6 - Remote Setup In Zoom

Student-visible text:

```text
Remote setup:

- join Zoom on time
- one person shares screen
- keep assignment directions nearby
- keep code editor visible
- use chat for links only when helpful
- say changes out loud before making them
```

**Instructor notes:**

- Remind students to manage audio and screen visibility.

**Transition cue:**

- "Start each session with alignment, not typing."

### Slide 7 - Start-Of-Session Checklist

Student-visible text:

```text
Before coding:

- confirm the assignment
- decide roles
- open the current files
- confirm the GitHub location
- identify the first small goal
- agree when to switch roles
```

**Instructor notes:**

- This prevents pairs from drifting into unstructured work.

**Transition cue:**

- "During coding, the conversation matters."

### Slide 8 - How To Talk While Coding

Student-visible text:

```text
Useful phrases:

- "What should happen next?"
- "Can you explain that line?"
- "Let's test before changing more."
- "Which requirement does this meet?"
- "Can we name this more clearly?"
- "What should we try first?"
```

**Instructor notes:**

- Give students language. Beginners often do not know how to collaborate out
  loud.

**Transition cue:**

- "Roles should move, not freeze."

### Slide 9 - Switch Roles Regularly

Student-visible text:

```text
Switch roles:

- every 10-15 minutes
- after a small feature works
- after a test passes
- when someone has been quiet too long

Both students should touch the work.
Both students should explain the work.
```

**Instructor notes:**

- Role switching keeps ownership shared.

**Transition cue:**

- "Testing is part of the conversation."

### Slide 10 - Test Before Changing More

Student-visible text:

```text
Pair rhythm:

1. choose a small change
2. say the plan
3. make the change
4. test it
5. explain what happened
6. then continue

Do not stack too many untested changes.
```

**Instructor notes:**

- Connect to debugging and evidence habits.

**Transition cue:**

- "GitHub keeps the shared work from living on one computer only."

### Slide 11 - GitHub During Pair Work

Student-visible text:

```text
GitHub during pair work:

- know where the current version lives
- one person should not keep the only copy
- upload at the end of a work session
- partners should confirm access
- explain what changed
```

**Instructor notes:**

- Refer students to the GitHub Basics recording for detailed steps.

**Transition cue:**

- "Start by downloading the current version."

### Slide 12 - Download At The Start

Student-visible text:

```text
At the start:

1. Open the shared repository.
2. Download the current version if needed.
3. Extract the ZIP.
4. Open the correct folder.
5. Confirm both partners see the same files.
```

**Instructor notes:**

- Keep this beginner web workflow, not command-line Git.

**Transition cue:**

- "At the end, one active driver uploads."

### Slide 13 - Upload At The End

Student-visible text:

```text
At the end:

1. Save all files.
2. Test the project.
3. Upload the updated files.
4. Write a short commit message.
5. Confirm the files appear in GitHub.
6. Tell your partner the update is posted.
```

**Instructor notes:**

- Emphasize one active upload at the end.

**Transition cue:**

- "The biggest beginner risk is overwriting each other."

### Slide 14 - Avoid Overwriting Each Other

Student-visible text:

```text
Avoid overwriting:

- do not both upload separate versions
- ask before replacing files
- download the latest version first
- keep a backup if unsure
- talk before deleting anything

When in doubt, pause and ask.
```

**Instructor notes:**

- This intentionally avoids branch/merge teaching.

**Transition cue:**

- "AI can support a pair, but it should not replace the pair."

### Slide 15 - AI During Pair Work

Student-visible text:

```text
AI during pair work:

- both partners read the response
- both partners discuss it
- both partners test any change
- both partners must understand submitted code

Prompt boundary:

"Do not rewrite it for us.
Explain the issue and ask one question first."
```

**Instructor notes:**

- Connect to the AI Prompting Basics bonus module.
- Reinforce assignment-specific AI rules.

**Transition cue:**

- "Disagreement is normal. Use a process."

### Slide 16 - When You Disagree

Student-visible text:

```text
When you disagree:

- check the assignment requirements
- test both ideas if small
- ask which version is easier to explain
- use evidence, not volume
- ask the instructor when stuck
```

**Instructor notes:**

- Keep collaboration emotionally safe and concrete.

**Transition cue:**

- "Good pair work leaves evidence."

### Slide 17 - Evidence Of Good Pair Work

Student-visible text:

```text
Good pair work means:

- both students can explain the result
- roles were shared
- code was tested
- GitHub has the current version
- the submission names what changed
- questions were asked early
```

**Instructor notes:**

- This can be used as a participation/evidence lens if desired.

**Transition cue:**

- "The closing checklist is what students should remember in Zoom."

### Slide 18 - Closing Checklist

Student-visible text:

```text
Remote pair checklist:

- decide roles
- share screen
- keep requirements visible
- talk through changes
- test often
- rotate roles
- upload once at the end
- confirm GitHub access
```

**Instructor notes:**

- Close with practical behavior.
- Remind students that paired work is practice for communication, not a way to
  offload responsibility.

**Transition cue:**

- "Good collaboration is visible in both the code and the explanation."
