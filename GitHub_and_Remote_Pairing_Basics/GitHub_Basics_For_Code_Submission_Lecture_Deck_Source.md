# GitHub Basics For Code Submission Lecture Deck Source

**Reusable Bonus Recording**  
**Audience:** Beginning programming, web development, and algorithms students  
**Working Title:** GitHub Basics - Submitting Code For Grading

---

# Session Purpose

This bonus lecture introduces GitHub as the primary place where students store
and submit code for grading.

The goal is practical course use, not full Git mastery. Students should leave
able to open a repository, organize lab folders, upload files, download current
work, and submit a useful GitHub link.

# Slide-By-Slide Source

### Slide 1 - GitHub Is Where Your Code Lives

Student-visible text:

```text
GitHub Basics

For this program:

GitHub is where your code lives.

It helps you:

- store code
- preserve progress
- submit work for grading
- share work when allowed
```

**Instructor notes:**

- State clearly that GitHub is not optional decoration.
- Schoology may still be used to submit a link or confirmation, but the code
  itself should live in GitHub unless the assignment says otherwise.

**Transition cue:**

- "We are using GitHub in a beginner-friendly way first."

### Slide 2 - What GitHub Is For In This Course

Student-visible text:

```text
In this course, GitHub is used to:

- keep a current copy of your work
- organize labs and assignments
- submit code for grading
- show README evidence and reflection
- recover work if a computer has problems
```

**Instructor notes:**

- Connect this to grading workflow.
- Mention that programming work includes code plus explanation/evidence.

**Transition cue:**

- "There are also things we are not trying to master yet."

### Slide 3 - What GitHub Is Not Yet

Student-visible text:

```text
Not yet:

- command-line Git
- branching
- merging
- pull requests
- professional team workflow
- advanced conflict resolution

For now:

Upload, download, organize, submit.
```

**Instructor notes:**

- This prevents overload.
- Students will see deeper GitHub later in the program.

**Transition cue:**

- "First, the basic vocabulary."

### Slide 4 - Repository, Folder, File

Student-visible text:

```text
Repository:
the main project storage space.

Folder:
a place to organize related files.

File:
one item in the project.

Example:

Course_Repository / Lab_03 / script.js
```

**Instructor notes:**

- Use simple file-cabinet analogy if useful.
- Keep terminology practical.

**Transition cue:**

- "A clear folder pattern makes grading and recovery easier."

### Slide 5 - Recommended Lab Folder Pattern

Student-visible text:

```text
Recommended pattern:

Course_Repository/
  Lab_01/
    README.md
    code file(s)
  Lab_02/
    README.md
    code file(s)
  Lab_03/
    README.md
    code file(s)

One lab, one folder.
```

**Instructor notes:**

- If a specific course uses a different pattern, the assignment wins.
- Emphasize consistency.

**Transition cue:**

- "The README is not extra. It is part of the submission."

### Slide 6 - README.md Is Part Of The Submission

Student-visible text:

```text
README.md usually explains:

- what the lab does
- how to run or view it
- evidence or test results
- assumptions
- reflection
- AI-use note, if required

Code shows what you built.
README explains what you understand.
```

**Instructor notes:**

- Connect to grading evidence.
- Students often submit only a code file; this slide counters that.

**Transition cue:**

- "Now let's look at how work gets into GitHub."

### Slide 7 - Creating Or Opening A Repository

Student-visible text:

```text
At the start:

1. Sign in to GitHub.
2. Open the course repository.
3. If creating a new repository, use a clear name.
4. Keep the repository school-appropriate.
5. Follow instructor directions for visibility.
```

**Instructor notes:**

- Avoid prescribing public/private unless the course does.
- Remind students to use their SWTC account/email if required.

**Transition cue:**

- "Sometimes you need to download the current work first."

### Slide 8 - Downloading Code From GitHub

Student-visible text:

```text
To download code:

1. Open the GitHub repository.
2. Click Code.
3. Choose Download ZIP.
4. Extract the ZIP folder.
5. Open the extracted folder in your editor.
6. Run or preview the project.
```

**Instructor notes:**

- Stress extracting the ZIP before editing.
- Beginners often edit files inside a compressed folder.

**Transition cue:**

- "After downloading, make sure you opened the right folder."

### Slide 9 - Opening Downloaded Code

Student-visible text:

```text
After downloading:

- extract the ZIP
- open the extracted folder
- check that expected files are present
- run or preview the project
- confirm you are editing the correct copy

Do not edit a random old download.
```

**Instructor notes:**

- This is a common failure point.
- For web projects, mention opening the folder in the editor and previewing the
  HTML as instructed.

**Transition cue:**

- "When your work changes, upload the changed files."

### Slide 10 - Uploading Updated Files

Student-visible text:

```text
To upload changed files:

1. Open the GitHub repository.
2. Click Add file.
3. Choose Upload files.
4. Drag the updated files or folder.
5. Add a short message.
6. Click Commit changes.
7. Confirm the files appear in GitHub.
```

**Instructor notes:**

- This is the beginner web interface workflow.
- Avoid command-line Git in this bonus lecture.

**Transition cue:**

- "The message should say what changed."

### Slide 11 - Commit Message: Name The Change

Student-visible text:

```text
Use short commit messages:

- Add lab 03 solution
- Update README evidence
- Fix button interaction
- Add test results
- Upload final version

Avoid:

- stuff
- final final
- changes
- idk
```

**Instructor notes:**

- Explain that a commit message is a label for the saved change.
- Keep it lightweight.

**Transition cue:**

- "For grading, the instructor needs the right link."

### Slide 12 - Submitting For Grading

Student-visible text:

```text
Submitting for grading:

1. Open the correct repository or lab folder.
2. Copy the URL.
3. Submit the link where the assignment says.
4. Check that the link opens.
5. Make sure the latest files are visible.

GitHub is the source of the code.
Schoology may collect the link.
```

**Instructor notes:**

- Make the GitHub/Schoology relationship explicit.
- If the course asks for a specific file link, mention that assignment
  directions override the general rule.

**Transition cue:**

- "Before submitting, check what you are uploading."

### Slide 13 - Do Not Upload Blindly

Student-visible text:

```text
Before uploading:

- save all files
- test the page or program
- include the correct files
- include README.md if required
- avoid random ZIP uploads
- remove unrelated files

Upload what you mean to submit.
```

**Instructor notes:**

- Students may upload a ZIP rather than useful files; discourage unless
  explicitly requested.
- This matters for grading clarity.

**Transition cue:**

- "When partners are involved, the overwrite risk gets bigger."

### Slide 14 - Avoid Overwriting Work

Student-visible text:

```text
Before replacing files:

- ask if anyone changed anything
- download the latest version
- compare what changed
- keep a backup if unsure
- do not overwrite silently

When in doubt, ask before uploading.
```

**Instructor notes:**

- This is beginner-level conflict prevention.
- Do not teach branching/merging here.

**Transition cue:**

- "For paired work, use one simple rule."

### Slide 15 - Paired Work Rule

Student-visible text:

```text
Paired work rule:

One active driver uploads at the end of the session.

Partners download after the upload is complete.

Do not both edit separate copies and upload over each other.
```

**Instructor notes:**

- This is intentionally simple.
- It avoids parallel editing conflicts before students learn Git branching.

**Transition cue:**

- "Most problems come from a few repeated mistakes."

### Slide 16 - Common Mistakes

Student-visible text:

```text
Common mistakes:

- submitting the wrong link
- forgetting README.md
- uploading old files
- editing inside a ZIP folder
- uploading only screenshots
- forgetting required data files
- submitting code that was not tested
```

**Instructor notes:**

- Keep the tone practical.
- The goal is fewer grading surprises.

**Transition cue:**

- "If you are stuck, ask for help with the specific step."

### Slide 17 - Getting Help

Student-visible text:

```text
When asking for help, include:

- course and assignment
- repository link
- what you expected
- what happened instead
- screenshot if useful
- the step where you got stuck

Do not just say:
"GitHub is not working."
```

**Instructor notes:**

- This aligns with debugging habits.
- Encourage specific help requests.

**Transition cue:**

- "The closing checklist is the survival version."

### Slide 18 - Closing Checklist

Student-visible text:

```text
Before you submit:

- correct repository
- correct lab folder
- code files present
- README present
- latest version uploaded
- link opens
- assignment directions followed

GitHub should show the work you want graded.
```

**Instructor notes:**

- This can become a handout/checklist item.
- Close by reminding students that GitHub will become more advanced later, but
  this is enough for early submissions.

**Transition cue:**

- "Good organization makes your work easier to grade and easier to recover."
