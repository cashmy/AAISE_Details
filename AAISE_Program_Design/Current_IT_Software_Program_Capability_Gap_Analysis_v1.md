# Current IT Software Program Capability Gap Analysis v1

## Purpose

This document provides a first-pass analysis of the current Southwest Tech IT
Software Developer curriculum against the emerging AAISE design framework.

It is not a final redesign proposal.

Its purpose is to identify where the current program already provides useful
alignment, where the largest gaps appear, and where an AI-injected bridge
version may be most feasible before a future AAISE successor program is fully
designed.

---

## Source Context

This analysis is based on the current course list in:

- [SWTC-IT Curr.xlsx](D:/@Job%20Application/Southwest%20Tech/Curriculum_Design/SWTC-IT%20Curr.xlsx)

The following local assumptions are also included based on user guidance:

- the `10-152` courses are the primary software program courses
- most non-`10-152` courses are state-mandated general education requirements
  and are expected to remain in both versions
- `10-151-101 Introduction to Security` may be considered for replacement
- semesters 3 and 4 are more open to aggressive change
- the first-semester `10-152` courses already have optional bridge-oriented
  titles aligned with the AI-injected direction

## Initial Read of the Overall Structure

The current program is stronger than a purely legacy software curriculum, but
it is still organized primarily as a conventional software development pathway
with AI appearing later and somewhat selectively.

That matters.

This is not a curriculum with no useful AI-era building blocks. In fact, the
current version already contains several courses that could support a stronger
bridge design:

- Python and advanced Python
- algorithms
- SQL and advanced SQL
- containers and cloud
- AI-Driven Systems Analysis
- Machine Learning and AI
- Enterprise Data Systems & API Architecture

At the same time, the current structure still reads more like:

`traditional software program + several modern/AI-relevant additions`

than:

`a program intentionally architected around the mixed workforce models now
shaping software practice`

That distinction is important.

## Workforce Model Coverage: Current State

Using the current AAISE workforce model language, the present curriculum appears
to distribute unevenly across the four workforce models.

### Workforce Model 1. Native

This is currently the strongest area of coverage.

The program clearly supports conventional software foundations through:

- Python
- web development
- algorithms
- SQL
- C#
- ASP.NET
- C++
- mobile development
- agile/capstone experience

The underlying structure still assumes conventional software development as the
primary organizing logic.

### Workforce Model 2. AI-Assisted

This area is currently weak in explicit form.

The curriculum likely supports some indirectly useful habits, such as coding,
debugging, and documentation, but the current course titles and descriptions do
not yet appear to frame AI-assisted workflow as a formal graduate capability.

This is a significant gap because AI-assisted practice is one of the most
immediate workforce realities students will encounter.

### Workforce Model 3. AI-Injected

This area is emerging but uneven.

The strongest signals appear in:

- `10-152-127` AI-Driven Systems Analysis
- `10-152-133` Enterprise Data Systems & API Architecture
- parts of cloud, data, and application development coursework that could be
  refactored toward intentional AI-supported solutions

However, this model is not yet fully distributed across the program as a
governing design logic.

At present, it appears more as a later-stage concentration area than as a
program-wide architectural throughline.

### Workforce Model 4. AI-Embedded

This area appears present only in partial form.

The best current support likely comes from:

- statistics
- SQL and advanced SQL
- advanced Python
- Machine Learning and AI
- Enterprise Data Systems & API Architecture

Even so, the current program does not yet appear to frame internal AI-enabled
business systems, data-driven operational logic, and governed AI-enabled system
behavior as a coherent educational target.

## Capability Alignment: Current Strengths

When viewed through the AAISE graduate capability model, the current program
already contains several meaningful strengths.

### Strength 1. Strong software foundation base

The existing curriculum already invests substantially in conventional software
development skills.

This supports the foundational capability groups related to:

- software foundations
- debugging and programming fluency
- web and application development
- systems implementation

That is a valuable base and should not be discarded lightly.

### Strength 2. Useful data and platform stack

The presence of SQL, advanced SQL, advanced Python, containers, cloud, and
enterprise data architecture creates a practical technical stack that can
support stronger AI-era applications if reframed appropriately.

This is especially useful for a bridge model because it means the current
program is not starting from zero.

### Strength 3. Emerging AI-era anchor courses already exist

Courses such as `AI-Driven Systems Analysis`, `Machine Learning and AI`, and
`Enterprise Data Systems & API Architecture` provide visible footholds for
future direction.

These may become important anchor points for both bridge design and eventual
successor-program divergence.

### Strength 4. Semesters 3 and 4 offer redesign leverage

Because later semesters are more open to change, they provide a realistic space
for stronger AI-injected experimentation and more substantial restructuring
without forcing immediate total redesign of the entire program.

This is strategically useful.

## Capability Gaps: Current State

The current program also shows several important gaps relative to the AAISE
target model.

### Gap 1. AI-assisted workflow capability is not yet formalized

The program does not yet appear to teach governed AI-assisted work as an
explicit capability.

This includes gaps in areas such as:

- AI-supported coding workflow
- prompt and context discipline
- evaluation of AI outputs
- revision and rejection of weak generated results
- authorship accountability in AI-supported work

Given current workforce reality, this is one of the largest immediate gaps.

### Gap 2. AI appears too late to shape the whole program

The strongest explicit AI signals do not appear until later semesters.

This creates a sequencing problem.

If AI-era thinking enters only after the program's primary habits and mental
models are already formed, students may interpret AI as an added topic rather
than as a change in workflow, architecture, and design conditions.

Your proposed alternate titles for first-semester courses already point toward a
solution to this problem:

- `10-152-117` Foundations of Programming for AI-Augmented Engineers
- `10-152-118` Web Foundations for AI-Augmented Engineers
- `10-152-119` Algorithmic Thinking for AI-Augmented Engineers

These titles are useful because they begin reframing the program much earlier
without discarding foundational content.

### Gap 3. AI-injected thinking is not yet a program-wide throughline

Although some current courses support AI-related concepts, the curriculum does
not yet appear to be architected around intentional AI injection as a governed
design practice.

This makes it easier for AI to be interpreted as:

- a specialty topic
- a later elective-like layer
- a single-course concern
- a machine learning add-on

rather than as a cross-program application design reality.

### Gap 4. AI-embedded systems are only partially represented

The current program includes several ingredients that relate to AI-embedded
systems, but they do not yet appear to be connected into a coherent capability
path.

Students may gain exposure to data, analytics, machine learning, APIs, and
cloud systems without necessarily developing a clear model of how AI becomes
part of internal organizational workflow, decision support, transformation, and
operational logic.

### Gap 5. Architectural and systems thinking may still be too localized

The current program contains systems-related work, but much of the visible
structure still appears course-centric and technology-centric.

The AAISE target model requires a stronger habit of:

- framing the system before the feature
- defining AI's role before implementation
- reasoning about boundaries, failure modes, and integration consequences
- distinguishing tool use from architectural integration

Some of this may already be emerging in `AI-Driven Systems Analysis`, but it
does not yet appear to be distributed strongly enough across the full pathway.

### Gap 6. Validation, uncertainty handling, and governed use need stronger emphasis

The current course list suggests strong hands-on technical exposure, but it does
not yet clearly signal sustained attention to:

- uncertainty honesty
- validation of AI outputs
- fallback behavior
- traceability of decisions
- human governance over AI-supported work

These capabilities are increasingly important in both AI-assisted and
AI-injected environments.

## Program-Level Tension Points

Several tension points appear when the current program is compared to the future
AAISE direction.

### Tension 1. Broad language coverage versus strategic depth

The program includes Python, C#, C++, web, mobile, SQL, ASP.NET, cloud, and
data systems.

This gives breadth, but it may also create pressure on curricular depth.

In an AI-era redesign, some of this breadth may need to be reconsidered if it
prevents stronger development of higher-value architectural, AI-assisted,
AI-injected, or AI-embedded capabilities.

### Tension 2. Conventional software identity versus AI-era re-architecture

The current curriculum still carries the identity of a traditional software
developer program.

That identity is not wrong, but it may limit how fully the program can be
reorganized around mixed workforce-model preparation unless some structural
decisions are revisited.

### Tension 3. Legacy continuity versus future coherence

The current program offers a practical base for bridge redesign, but some
elements may remain in place because they are convenient, familiar, or already
approved rather than because they are the best long-term carriers for the
future capability model.

This is exactly why the distinction between bridge version and successor program
matters.

## Likely Bridge Opportunities

Based on the current structure, several bridge opportunities appear promising.

### Opportunity 1. Reframe semester 1 as the new conceptual entry point

The optional titles you provided for the first-semester `10-152` courses are
strategically strong.

They suggest a way to preserve foundational content while changing the meaning
frame around it early:

- Python as programming foundations for AI-augmented engineers
- web development as web foundations for AI-augmented engineers
- algorithms as algorithmic thinking for AI-augmented engineers

This is likely one of the cleanest high-value bridge moves available.

### Opportunity 2. Formalize AI-assisted workflow across multiple courses

Rather than isolating AI use into one course, the bridge version could
introduce governed AI-assisted practice across:

- Python
- web development
- advanced Python
- SQL
- systems analysis
- agile/capstone

This would help students distinguish between useful leverage and shallow
dependence.

### Opportunity 3. Use semesters 3 and 4 for stronger AI-injected design work

Your note that semesters 3 and 4 are more open is important.

These semesters seem like the best place to:

- strengthen AI-injected system design
- introduce agentic and tool-orchestrated patterns where appropriate
- deepen API, cloud, data, and workflow integration
- align capstone and career experience more directly with AI-era practice

### Opportunity 4. Treat certain courses as likely successor-program pivot points

The courses most likely to become pivot points for future divergence appear to
include:

- `10-152-127` AI-Driven Systems Analysis
- `10-152-131` Machine Learning and AI
- `10-152-133` Enterprise Data Systems & API Architecture

These may become important leverage points for determining what belongs in the
bridge version versus what should later be re-architected more fully in the
AAISE successor model.

## Courses That May Need Closer Review

Without making final replacement recommendations yet, several areas likely
deserve special scrutiny in the next pass.

### `10-151-101` Introduction to Security

You noted that this course may be considered for replacement.

That makes it an especially important decision point because it sits in semester
1 and therefore affects the earliest shape of the bridge pathway.

### `10-152-128` C++ Programming

This course may or may not remain strategically valuable depending on how the
future capability model is prioritized.

Its value should likely be evaluated against what higher-priority AI-era
capabilities could occupy that space.

### `10-152-132` Mobile Development

This may still be useful, but its role should be tested against the broader
bridge and successor logic rather than assumed.

### Breadth across multiple programming stacks

The combined presence of Python, C#, C++, ASP.NET, web, mobile, and other stack
elements suggests a future need to ask:

is the current variety creating adaptive strength, or is some of it consuming
space that could be better used for stronger mixed-model preparation?

That question should remain open for now.

## Working Gap Summary

The current Southwest Tech IT Software Developer program provides a stronger
starting point for transition than a purely legacy software curriculum, but it
does not yet appear fully organized around the realities that the future AAISE
effort is trying to address.

Its strongest present alignment is with `Workforce Model 1: Native`, supported
by good conventional software foundations and a practical technical stack.

Its weakest area is currently the explicit development of `Workforce Model 2:
AI-Assisted` capability as a governed, teachable practice rather than an
informal side behavior.

`Workforce Model 3: AI-Injected` and `Workforce Model 4: AI-Embedded` are both
emerging in the current curriculum, but neither yet appears to function as a
fully coherent, program-wide design logic.

This suggests the current program is well positioned to support an AI-injected
bridge version, but that bridge will need deliberate reframing, redistribution
of emphasis, and stronger early integration if it is to meaningfully inform a
future AAISE successor program.
