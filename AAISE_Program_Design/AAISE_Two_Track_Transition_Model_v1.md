# AAISE Two-Track Transition Model v1

## Purpose

This document proposes a first-pass conceptual transition model for moving from
the current IT Software Developer program toward a future AAISE (Associates AI
Software Engineering) program.

It does not define final courses, final equivalencies, or final implementation
timelines.

Its purpose is to clarify why a two-track approach may be necessary, what each
track is meant to do, and how both tracks can work together during a transition
period.

---

## Why a Two-Track Model Is Needed

The current redesign challenge appears to contain two real needs at the same
time.

The first need is practical and immediate:

how to work with the currently approved IT Software Developer program in a way
that meaningfully incorporates AI-related capability development under current
governance conditions.

The second need is structural and forward-looking:

how to design a future program that reflects the realities of software work in
an AI-shaped environment rather than merely adding AI content to a pre-AI
program structure.

If only the first need is addressed, the result may be a useful bridge but not
a sufficient long-term model.

If only the second need is addressed, the result may be conceptually stronger
but harder to implement, approve, or transition into.

The two-track model exists because both needs are real and neither one fully
solves the problem by itself.

---

## The Two Tracks

### Track 1. AI-Injected Bridge Version of the Current Program

Track 1 uses the current approved IT Software Developer program as the starting
point for near-term redesign.

Its purpose is to create a more AI-relevant version of the current program
without requiring immediate abandonment of the existing structure.

This track is transitional by design.

It allows Southwest Tech to work within present governance conditions, begin
developing and testing AI-oriented curriculum logic, and support students who
will still be moving through the legacy program pathway during the overlap
period.

Track 1 is not merely cosmetic AI addition.

If done well, it should begin developing capabilities related to the new
Workforce Models while also revealing where the current structure can and cannot
carry the needed shift.

### Track 2. AAISE Successor Program

Track 2 is the design of a more coherent AI-era successor program rather than a
simple modification of the current one.

Its purpose is to create a degree structure intentionally aligned with the
mixed-state software environment students are entering.

This future program should be shaped by the realities of four Workforce Models:

- Native
- AI-Assisted
- AI-Injected
- AI-Embedded

Track 2 is not defined by novelty for its own sake.

Its role is to go beyond the limits of patching a legacy structure and to
design a program whose architecture better matches the emerging field.

---

## How the Two Tracks Relate

The two tracks should not be treated as isolated projects.

They are related in both directions.

Track 1 can inform Track 2 by revealing:

- what is easy to integrate into the current structure
- what becomes overloaded when AI capability is added
- what students may be able to transition through cleanly
- what kinds of content or capability do not fit well inside the legacy model

Track 2 can inform Track 1 by clarifying:

- which capabilities matter most
- which changes are worth making even in the bridge version
- which parts of the legacy structure should be treated as temporary rather than
  normative
- which future-aligned patterns can begin now without waiting for full program
  replacement

In this sense, Track 1 produces practical evidence and Track 2 provides longer
architectural direction.

---

## Why the Word "Bridge" Matters

The AI-injected revision of the current program should be understood as a
bridge, not as the final destination.

This matters because a bridge has a different design logic than an endpoint.

A good bridge should:

- improve the current student experience
- increase relevance under present conditions
- preserve continuity and employability
- make later transition easier
- expose where deeper future redesign is still needed

If the bridge is mistaken for the final model, there is a risk that the system
will stop at partial modernization and call it completion.

If the bridge is undervalued, there is a risk of designing a future program
without enough reality contact or implementation learning.

Both errors should be avoided.

---

## Shared Design Requirement: Workforce Model Alignment

Both tracks should be shaped by the same underlying workforce reality.

That means both the bridge version and the successor program should be designed
with awareness of four Workforce Models:

### Workforce Model 1. Native

Software is developed and delivered without official AI participation in either
the product or the approved development workflow.

In some environments, AI use may be culturally, managerially, or operationally
discouraged or prohibited, even if unofficial shadow use still occurs.

### Workforce Model 2. AI-Assisted

AI is used within the human workflow to support work, but AI is not part of the
delivered application or system itself.

This can include common low-barrier uses that many people already associate with
AI assistance, such as drafting emails, summarizing meetings, supporting search
and research, or helping with general workplace communication tasks.

In software contexts, it also includes stronger forms of workflow assistance
such as coding help, debugging support, documentation drafting, testing support,
comparison of options, and other development-time acceleration.

### Workforce Model 3. AI-Injected

AI is intentionally introduced into the solution architecture as part of the
application's designed behavior or supported workflow.

This is not merely "adding an AI feature" or attaching a chatbot.

It implies governed, purposeful integration in which the role, boundaries, and
value of AI are architecturally justified.

This can also include emerging agentic AI patterns in which AI participates in
multi-step operations, orchestrated tool use, or governed action flows inside a
designed system context, such as agent-style development operations, structured
tool-calling environments, or MCP-like integration patterns.

### Workforce Model 4. AI-Embedded

AI becomes part of the internal operating logic of the system or business
workflow itself, especially in relation to organizational data, analysis,
prediction, transformation, decision support, or generative operations.

Here AI is not peripheral. It participates in how the system functions
internally.

These models should not be treated as isolated specialties.

They represent the mixed reality graduates are likely to encounter.

The difference between the two tracks is not whether these models matter, but
how fully and structurally each track can respond to them.

---

## Shared Design Requirement: Capability Continuity

A second requirement shared by both tracks is capability continuity.

Even if the bridge and successor programs differ structurally, they should
still be built around overlapping capability foundations wherever possible.

This matters for at least three reasons:

- students may move between pathways
- faculty need continuity in what is being developed
- the institution needs a coherent basis for advising and equivalency

Examples of likely continuity areas include:

- software foundations
- problem framing and debugging
- governed AI-assisted practice
- systems and architectural thinking
- validation and uncertainty handling

The more clearly shared capabilities are identified, the easier later
transition design becomes.

---

## Shared Design Requirement: Honest Difference

Although the two tracks should remain aligned, they should not be forced into
artificial sameness.

The bridge version exists to improve and adapt the current structure.

The successor program exists to move beyond the limits of that structure where
needed.

This means some divergence is expected and healthy.

For example:

- some capabilities may appear only partially in the bridge version
- some future program elements may have no clean equivalent in the current
  structure
- some courses may serve as acceptable temporary carriers even if they are not
  ideal long-term homes

Design coherence does not require pretending both tracks are the same.

It requires clarity about what is shared, what is transitional, and what is
future-facing.

---

## Transition Period Logic

Because both program paths may overlap for at least one year, the transition
period needs its own design logic.

This period should not be treated as a temporary mess to clean up later.

It should be treated as part of the architecture.

During the overlap period, the model should ideally support:

- students finishing the legacy pathway without loss of value
- students beginning a revised bridge pathway with improved relevance
- students transitioning into a future program when appropriate
- faculty teaching with enough continuity to avoid collapse of delivery quality
- advisors making pathway decisions with understandable logic

In other words, the transition period is not a gap between models.

It is a real operating phase that needs to be designed intentionally.

---

## What Track 1 Must Accomplish

The AI-injected bridge version should accomplish at least the following:

- increase the present relevance of the approved current program
- begin developing capabilities tied to the four Workforce Models
- preserve employability in conventional software contexts
- create usable insight about what the current structure can and cannot support
- reduce the risk of students being stranded during program overlap
- provide practical evidence that can inform statewide discussion

Track 1 should therefore be judged not only by how much AI language appears in
it, but by whether it creates meaningful capability gain and transition value.

---

## What Track 2 Must Accomplish

The AAISE successor program should accomplish at least the following:

- provide a more coherent degree architecture for AI-era software work
- align more intentionally with the four Workforce Models
- preserve strong software foundations while modernizing the design target
- reduce dependence on legacy program assumptions where those assumptions no
  longer fit
- create a model that could be legible and adaptable beyond one local context

Track 2 should therefore be judged not only by originality, but by coherence,
clarity, workforce relevance, and adoptability.

---

## Risks the Two-Track Model Helps Avoid

This model helps avoid several predictable errors.

### Risk 1. Treating AI as only a tool layer

Without a two-track approach, the redesign may stop at shallow AI-assisted
tooling and fail to address deeper architectural and workflow realities.

### Risk 2. Mistaking the bridge for the final form

Incremental improvement of the current program may be valuable, but it should
not automatically define the long-term future degree.

### Risk 3. Designing a future model with weak transition logic

A strong new program can still fail in practice if it does not account for
student movement, overlap periods, and delivery constraints.

### Risk 4. Overstating certainty too early

The current state of redesign is still exploratory enough that a staged model
is more honest than pretending the final structure is already obvious.

---

## Working Transition Summary

The two-track model provides a way to hold together immediate action and
longer-term redesign.

Track 1 creates an AI-injected bridge from the current approved program.

Track 2 develops a more coherent AAISE successor aligned to the actual mixed
workforce environment emerging across software work.

The value of the model lies not only in having two tracks, but in governing the
relationship between them:

- shared workforce reality
- shared capability foundations
- honest difference where needed
- intentional transition design during overlap

This makes the transition model more than a scheduling convenience.

It becomes a design architecture for moving from legacy program logic toward a
stronger future program without pretending that either the current system or
the future state can be ignored.

## Next Questions

The next design-stage questions likely include:

- What shared capabilities should anchor both tracks most explicitly?
- Which parts of the current IT Software Developer program are strongest
  candidates for bridge-level AI injection?
- Where are the likely first major divergence points between the bridge and the
  successor model?
- What eventual equivalency or student transition logic may be needed once the
  current program details are mapped?
