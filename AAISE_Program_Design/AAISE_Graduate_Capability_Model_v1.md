# AAISE Graduate Capability Model v1

## Purpose

This document proposes a first-pass graduate capability model for a future
AAISE (Associates AI Software Engineering) program and for the transitional
AI-injected redesign work that may precede it.

It does not define final courses or final sequencing.

Its purpose is to clarify what kinds of capability students should be able to
demonstrate if the curriculum is to reflect the actual mixed-mode software
environment now emerging.

---

## Why Use a Capability Model

When curriculum redesign starts with courses alone, it is easy to preserve old
structures by habit and then add new topics on top.

A capability model reverses that order.

It asks first:

what should a graduate actually be able to do, understand, evaluate, and adapt
to in the real world?

Only after that should course structures, learning activities, and transition
paths be shaped in detail.

---

## Core Design Assumption

AAISE graduates should not be prepared for only one software reality.

They should be prepared to operate across multiple overlapping environments:

- native software development
- AI-assisted development
- AI-injected application development
- AI-embedded systems and workflows

This does not mean every graduate must become an expert in every advanced area.

It does mean graduates should leave with a coherent foundation that allows them
to function, learn, adapt, and contribute across these contexts.

---

## Capability Group 1. Software Foundations

Graduates should demonstrate durable software engineering fundamentals that
remain valuable with or without AI involvement.

This includes the ability to:

- frame problems clearly before jumping to solutions
- reason through logic, flow, and program behavior
- write, read, and revise code with purpose
- test, debug, and improve software methodically
- work with data structures, basic algorithms, and control flow
- understand application components, interfaces, and integration points
- communicate technical intent in writing and discussion

These capabilities remain foundational because AI does not remove the need for
judgment, diagnosis, or structured thinking.

In many cases, AI actually increases the value of these capabilities because it
raises the need for validation, discernment, and correction.

---

## Capability Group 2. AI-Assisted Development Practice

Graduates should be able to use AI as a development support mechanism without
becoming dependent on uncritical tool output.

This includes the ability to:

- use AI tools to accelerate drafting, coding, debugging, documentation, and
  testing tasks
- evaluate AI outputs for correctness, fit, and risk
- detect when AI output is shallow, misleading, or overconfident
- refine prompts, context, and constraints to improve results
- compare AI-generated options rather than accept the first plausible answer
- maintain authorship responsibility for final work

The goal here is not just tool familiarity.

The deeper capability is governed AI use.

Students should learn how to gain leverage from AI while preserving judgment
and quality control.

---

## Capability Group 3. AI-Injected Application Design

Graduates should be able to participate in the design and implementation of
applications that incorporate AI capabilities intentionally rather than
superficially.

This includes the ability to:

- identify when AI is and is not an appropriate addition to a system
- define the intended role of AI within an application or workflow
- distinguish between user-facing AI features and internal AI-supported logic
- account for boundaries, constraints, and failure modes in AI-enabled systems
- design supporting flows for retrieval, transformation, validation, and
  fallback behavior
- recognize that AI injection changes architecture, testing, and support needs

This capability group moves beyond using AI as a helper and toward building
software in which AI participation becomes part of the product or process.

---

## Capability Group 4. AI-Embedded Systems Awareness

Graduates should understand the role of AI inside business systems, workflows,
and data environments where AI becomes part of the system's operational logic.

This includes the ability to:

- understand descriptive, predictive, and generative or transformative AI use
  in practical business contexts
- recognize how business data quality affects AI outcomes
- reason about internal AI-supported workflows rather than only public-facing
  app features
- identify governance, privacy, reliability, and oversight concerns
- understand the difference between a demo feature and an operationally useful
  AI-enabled business process

This does not require every graduate to be a deep ML specialist.

It does require enough architectural and operational understanding to work in
environments where AI is part of how the system functions internally.

---

## Capability Group 5. Architectural and Systems Thinking

Graduates should be able to think beyond isolated code tasks and reason about
systems, structure, and consequences.

This includes the ability to:

- define what a system is trying to achieve before selecting implementation
  details
- identify components, boundaries, dependencies, and flows
- distinguish between symptoms and underlying causes
- evaluate tradeoffs rather than default to convenience
- understand how design decisions affect maintainability and change
- reason upward from implementation issues to architectural implications

This group is increasingly important in an AI era because tool fluency alone
does not create coherence.

Students need practice in seeing the whole system, not just generating local
output.

---

## Capability Group 6. Data, Context, and Input Quality Reasoning

Graduates should understand that AI output quality depends heavily on the
quality of data, retrieval, context, and input structure.

This includes the ability to:

- recognize that poor inputs often produce poor outputs
- distinguish between model issues, retrieval issues, data issues, and prompt
  issues
- reason about context boundaries and information completeness
- handle structured and unstructured information with care
- understand how missing, noisy, or misaligned data changes system behavior

This is especially important because many AI failures are misdiagnosed as model
problems when the real issue lies elsewhere in the system.

---

## Capability Group 7. Testing, Validation, and Uncertainty Handling

Graduates should be prepared to validate software and AI-related outputs in
contexts where uncertainty cannot always be removed in advance.

This includes the ability to:

- test software behavior systematically
- validate AI-assisted or AI-generated outputs against requirements and
  evidence
- recognize when certainty is not yet justified
- design fallback paths, review loops, and bounded failure handling
- communicate limitations and uncertainty honestly
- avoid treating plausible output as automatically correct output

This matters because AI often increases output volume faster than it increases
trustworthiness.

Students therefore need stronger validation habits, not weaker ones.

---

## Capability Group 8. Human Governance and Professional Judgment

Graduates should understand that responsibility for quality, fit, and
acceptance remains human, even when AI participates in the work.

This includes the ability to:

- maintain accountability for decisions and delivered work
- decide when to accept, revise, reject, or escalate AI-supported output
- recognize bias, overreach, and false confidence in generated material
- preserve ethical, legal, and professional boundaries
- understand that AI can expand capability without removing responsibility

This group helps prevent the collapse of professional judgment into passive
tool consumption.

---

## Capability Group 9. Adaptability and Continuous Learning

Graduates should leave with the ability to keep learning in a rapidly changing
technical environment.

This includes the ability to:

- acquire new tools and concepts without losing grounding
- ask useful technical questions
- compare alternatives and learn enough to make informed choices
- update approaches when evidence or conditions change
- move between conventional, transitional, and more AI-intensive environments

This capability is especially important because the field is changing faster
than any single curriculum can perfectly stabilize.

The goal is not only current readiness, but durable adaptability.

---

## Cross-Cutting Program Principle

The graduate should not emerge as:

- only a conventional developer with minimal AI familiarity
- only a tool user with weak software foundations
- only a partial AI enthusiast with unclear system understanding

Instead, the graduate should emerge as a beginning software professional who
can think clearly, work responsibly, and contribute across a mixed development
landscape shaped by both conventional and AI-mediated practice.

---

## Working Capability Summary

An AAISE-aligned graduate capability model should balance at least five things
at once:

- durable software fundamentals
- governed AI-assisted practice
- ability to build or support AI-injected applications
- awareness of AI-embedded business system realities
- architectural judgment strong enough to adapt across change

This is intentionally broader than a narrow "learn AI tools" model and more
practical than a purely theoretical AI curriculum detached from real software
work.

---

## Design Implications

If this capability model is directionally correct, several implications follow.

### 1. The current curriculum should be evaluated against capability gaps

The question is not only what courses exist, but what capabilities they do or
do not actually develop.

### 2. AI injection should be judged by capability gain, not by AI mention count

Adding AI vocabulary to a course is not the same as developing meaningful
student capability.

### 3. A future AAISE program may require different structural emphasis

If these capabilities are taken seriously, the eventual successor program may
need more intentional architecture than the current program can comfortably
carry.

### 4. Transition planning should preserve shared foundations

The easier it is to identify foundational capabilities common to both the
bridge and successor models, the easier it will be to support student movement
across overlapping program periods.

---

## Next Questions

The next design-stage questions likely include:

- Which capabilities should be introduced in the bridge version versus reserved
  for fuller development in the successor program?
- Which existing courses map most naturally to these capability groups?
- Where are the biggest current gaps between the legacy curriculum and the
  emerging capability target?
- How should these capabilities be expressed in governance-friendly language for
  broader review and adoption?
