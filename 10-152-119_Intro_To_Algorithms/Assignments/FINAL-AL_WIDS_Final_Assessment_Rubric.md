# WIDS FINAL ASSESSMENT RUBRIC

**10-152-119 Algorithmic Problem Solving**

---

# Purpose

This rubric supports the two-part final assessment for `10-152-119 Algorithmic
Problem Solving`.

It is designed to be WIDS-friendly and easy for non-technical reviewers to
follow. The rubric is divided into the same two parts as the final assessment:

1. **Part 1 - Applied Solution Set**
2. **Part 2 - Explanation Defense**

This rubric intentionally uses only technical course competencies. It does not
include CORE abilities for this final assessment.

---

# WIDS Course Competency Alignment

The final assessment aligns to the following course competencies from the WIDS
course competency framework:

| Code | WIDS Course Competency |
| --- | --- |
| CC1 | Analyze problems to define algorithmic solutions |
| CC2 | Select and use data structures to support algorithmic solutions |
| CC3 | Implement and test introductory algorithms using Python |
| CC4 | Evaluate correctness, efficiency, and tradeoffs |
| CC5 | Connect algorithmic thinking to AI, analytics, data modeling, and responsible tool use |

| Assessment Part | Weight | Primary Evidence |
| --- | ---: | --- |

# Performance Scale

| Score | Level | General Meaning |
| ---: | --- | --- |
| 4 | Exceeds | Work is accurate, complete, well-supported, and clearly explained |
| 3 | Meets | Work satisfies the requirement with minor gaps that do not prevent assessment |
| 2 | Developing | Work is partially successful but has important gaps, weak evidence, or limited explanation |
| 1 | Needs Improvement | Work is minimal, unclear, substantially incorrect, or difficult to assess |
| 0 | Missing | Required evidence is not submitted or not attempted |

# Part 1 Rubric - Applied Solution Set

**Weight:** 70% of final assessment

Part 1 evaluates the submitted algorithmic work. Working solutions carry the
largest share of this score because producing functioning algorithmic artifacts
is the primary evidence for this course.

The following competency blocks are formatted for easier entry into Schoology.
The suggested weights are for Part 1 only and total 100% of the Part 1 score.

If Schoology supports a `0 - Missing` level, use it when required evidence is
not submitted or not attempted. If Schoology only uses four rubric levels,
missing work may be entered as no score or the lowest available score according
to local grading practice.

## T1. Problem Framing and Algorithmic Analysis

**WIDS Alignment:** CC1 - Analyze problems to define algorithmic solutions  
**Suggested Part 1 Weight:** 10%  
**Evidence:** problem statements, inputs, outputs, assumptions, constraints,
ambiguity notes, edge cases, README explanations

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Clearly frames all three final tasks with precise problem statements, inputs, outputs, assumptions, constraints, ambiguity notes, and relevant edge cases before or alongside implementation |
| **3 - Meets** | Defines the main problem elements and intended approach for the final tasks with minor gaps that do not prevent meaningful implementation or review |
| **2 - Developing** | Provides partial framing, but important inputs, outputs, constraints, assumptions, ambiguity, or edge cases are missing or unclear |
| **1 - Needs Improvement** | Begins coding or using tools with little clear problem definition, weak assumptions, or an unclear algorithmic approach |

## T2. Data Structures and Representation

**WIDS Alignment:** CC2 - Select and use data structures to support
algorithmic solutions  
**Suggested Part 1 Weight:** 10%  
**Evidence:** lists, dictionaries, sets, records, request/resource
representations, duplicate-detection structures, ranking tables, representation
summaries

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Selects and uses data structures purposefully across the decision, duplicate-detection, and recommendation tasks; clearly explains how representation supports correctness, lookup, comparison, or ranking |
| **3 - Meets** | Uses reasonable data structures and representations for the required tasks with minor inefficiencies or explanation gaps |
| **2 - Developing** | Uses some structures correctly, but representation choices are awkward, fragile, inefficient, incomplete, or weakly justified |
| **1 - Needs Improvement** | Uses inappropriate or unclear structures that interfere with the solution or make the algorithm difficult to review or explain |

## T3. Algorithm Implementation and Testing

**WIDS Alignment:** CC3 - Implement and test introductory algorithms using
Python  
**Suggested Part 1 Weight:** 30%  
**Evidence:** Python files, working or mostly working solutions, normal tests,
edge tests, expected/actual output, duplicate-detection results,
recommendation/ranking output

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Implements all three final tasks accurately and readably; solutions run or simulate correctly, required tests are present, and results support the intended algorithmic behavior |
| **3 - Meets** | Implements the three final tasks with minor errors, incomplete cases, or small readability issues that do not prevent assessment of the intended solutions |
| **2 - Developing** | Implementations are partially functional but contain logic gaps, incomplete task work, fragile behavior, limited testing, or unclear connection to the assigned problem |
| **1 - Needs Improvement** | Implementations are mostly nonfunctional, missing, or not meaningfully connected to the final tasks |

## T4. Correctness, Efficiency, and Tradeoff Evaluation

**WIDS Alignment:** CC4 - Evaluate correctness, efficiency, and tradeoffs  
**Suggested Part 1 Weight:** 15%  
**Evidence:** correctness checks, comparison of approaches, timing or
comparison tables, limitations, tradeoff explanations, efficiency vocabulary,
readability and maintainability discussion

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Evaluates correctness, efficiency, readability, limitations, and tradeoffs using clear evidence and appropriate introductory algorithm vocabulary |
| **3 - Meets** | Provides a reasonable evaluation of correctness, efficiency, limitations, or tradeoffs with minor gaps in evidence or explanation |
| **2 - Developing** | Makes limited or mostly unsupported claims about correctness, efficiency, limitations, or tradeoffs |
| **1 - Needs Improvement** | Does not meaningfully evaluate whether the solutions work, fit the problem, or compare reasonably to another approach where required |

## T5. Observable Algorithm Behavior and Communication Evidence

**WIDS Alignment:** CC1, CC3, CC4 - Problem framing, implementation/testing,
and evaluation evidence  
**Suggested Part 1 Weight:** 25%  
**Evidence:** README, test tables, comparison tables, timing tables,
representation tables, ranking tables, expected/actual results, known issues,
organized GitHub submission

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Provides clear, organized, reviewable evidence that makes algorithm behavior visible across all three tasks and connects that evidence to the README explanation |
| **3 - Meets** | Provides appropriate evidence and an organized enough submission to support review, with minor clarity or completeness gaps |
| **2 - Developing** | Provides limited evidence, weak README explanation, missing tables, or organization issues that make the work harder to assess |
| **1 - Needs Improvement** | Provides little evidence beyond code output or claims that the code works; submission is difficult to review or missing required pieces |

## T6. AI/Data Foundations and Responsible Tool Use

**WIDS Alignment:** CC5 - Connect algorithmic thinking to AI, analytics, data
modeling, and responsible tool use  
**Suggested Part 1 Weight:** 10%  
**Evidence:** AI-use note, no-AI statement, previous-work reference note,
validation of AI/tool output, recommendation/ranking explanation, assumptions,
limitations, human decision notes

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Clearly discloses AI/tool use and previous-work reference use when applicable; validates output, explains what was accepted, changed, rejected, reused, or verified, and connects the recommendation task to AI/data reasoning responsibly |
| **3 - Meets** | Provides required AI/tool or previous-work disclosure and basic validation or explanation when applicable |
| **2 - Developing** | Provides incomplete disclosure, weak validation, unclear attribution, or limited explanation of AI/tool or previous-work contributions |
| **1 - Needs Improvement** | Relies on AI/tool output or previous work with little understanding, validation, explanation, or required disclosure |

# Part 2 Rubric - Explanation Defense

**Weight:** 30% of final assessment

Part 2 evaluates whether the student can explain the submitted work. This part
is not designed as a gotcha. It verifies understanding and can raise the final
assessment score when students can credibly explain working or mostly working
solutions. Questions may be standardized, personalized, or a blend of both.

The following explanation-defense blocks are formatted for easier entry into
Schoology. The suggested weights are for Part 2 only and total 100% of the Part
2 score.

If Schoology supports a `0 - Missing` level, use it when the student does not
attempt the explanation or when required explanation evidence is not provided.
If Schoology only uses four rubric levels, missing explanation may be entered
as no score or the lowest available score according to local grading practice.

## E1. Submitted Solution Walkthrough

**WIDS Alignment:** CC1 - Analyze problems to define algorithmic solutions;
CC3 - Implement and test introductory algorithms using Python  
**Suggested Part 2 Weight:** 25%  
**Evidence:** spoken or written walkthrough, references to submitted files,
input-to-output explanation, explanation of main logic flow

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Explains the submitted solution flow accurately from input to output and references specific submitted work, code sections, or task evidence |
| **3 - Meets** | Explains the main solution flow with minor gaps that do not prevent understanding of the submitted work |
| **2 - Developing** | Explains parts of the submitted solution but misses important logic, sequence, or task-specific details |
| **1 - Needs Improvement** | Gives a vague explanation that is difficult to connect to the submitted work or cannot describe the main solution flow clearly |

## E2. Correctness and Evidence Explanation

**WIDS Alignment:** CC3 - Implement and test introductory algorithms using
Python; CC4 - Evaluate correctness, efficiency, and tradeoffs  
**Suggested Part 2 Weight:** 20%  
**Evidence:** explanation of tests, traces, expected/actual results, comparison
tables, ranking tables, examples, README evidence

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Clearly connects tests, traces, tables, charts, examples, or README evidence to why the submitted solution works or mostly works |
| **3 - Meets** | Explains basic correctness evidence with minor gaps or limited detail |
| **2 - Developing** | Identifies evidence but has difficulty explaining how it supports correctness or expected behavior |
| **1 - Needs Improvement** | Makes unsupported claims that the solution works or gives little meaningful explanation of correctness evidence |

## E3. Assumptions, Edge Cases, and Limitations

**WIDS Alignment:** CC1 - Analyze problems to define algorithmic solutions;
CC4 - Evaluate correctness, efficiency, and tradeoffs  
**Suggested Part 2 Weight:** 20%  
**Evidence:** explanation of assumptions, ambiguity, edge cases, known issues,
failure conditions, limitations, possible improvements

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Accurately identifies meaningful assumptions, edge cases, limitations, or failure conditions and explains how they affect the submitted solution |
| **3 - Meets** | Identifies at least one meaningful assumption, edge case, limitation, or failure condition with reasonable explanation |
| **2 - Developing** | Identifies a weak, incomplete, or only partly relevant assumption, edge case, or limitation |
| **1 - Needs Improvement** | Struggles to identify where the solution may fail, what it assumes, or what limitations remain |

## E4. Tradeoff and Efficiency Explanation

**WIDS Alignment:** CC2 - Select and use data structures to support
algorithmic solutions; CC4 - Evaluate correctness, efficiency, and tradeoffs  
**Suggested Part 2 Weight:** 20%  
**Evidence:** explanation of approach choice, data structure choice,
readability, efficiency, correctness, simplicity, maintainability, comparison
between approaches

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Clearly explains tradeoffs among approach, data structure, readability, correctness, and efficiency using appropriate introductory vocabulary and submitted evidence |
| **3 - Meets** | Provides a reasonable tradeoff or efficiency explanation with minor gaps |
| **2 - Developing** | Gives a limited explanation that is only partly connected to the submitted solution or evidence |
| **1 - Needs Improvement** | Provides little meaningful explanation of tradeoffs, efficiency, approach choice, or data structure choice |

## E5. AI/Tool and Reference-Use Accountability

**WIDS Alignment:** CC5 - Connect algorithmic thinking to AI, analytics, data
modeling, and responsible tool use  
**Suggested Part 2 Weight:** 15%  
**Evidence:** explanation of AI/tool use, no-AI statement, previous-work
reference explanation, validation steps, accepted/changed/rejected output,
student ownership of submitted work

| Level | Description |
| ----- | ----------- |
| **4 - Exceeds** | Clearly explains what AI/tooling or previous work contributed, how it was checked, and what the student changed, accepted, rejected, reused, or adapted |
| **3 - Meets** | Explains AI/tool or reference use and basic validation with minor gaps; or provides a clear no-AI/no-reference statement when applicable |
| **2 - Developing** | Provides partial explanation of AI/tool or reference use but weak validation, unclear attribution, or limited ownership explanation |
| **1 - Needs Improvement** | Cannot clearly explain AI/tool or reference contribution, validation, ownership, or required disclosure |

If AI was not used, a simple no-AI statement is sufficient for the disclosure
portion. If previous work was not referenced, a simple no-previous-work
statement is sufficient for the reference-use portion. The instructor may also
use a hypothetical tool-use question to assess responsible tool-use judgment.

# Scoring Notes

- Functional submitted work should receive substantial credit when it solves or
  mostly solves the assigned task, even when the implementation is not elegant.
- Part 2 should verify understanding and ownership of submitted work, not punish
  the student for using approved support.
- Memorized or rehearsed explanation can still count when it accurately
  explains the submitted work.
- Standardized Part 2 questions are acceptable when they verify understanding
  of the submitted work and avoid unrelated recall.
- Higher scores require students to explain evidence, assumptions, tradeoffs,
  and AI/tool use with increasing independence and accuracy.
- If a student submits working but poorly structured code, score the working
  solution in Part 1 and use Part 2 to assess whether the student can identify
  weaknesses and possible improvements.
