# 🧭 INSTRUCTOR SCORING GUIDE (ISG-01)

**HTML, CSS & JavaScript — SWTC**

---

## 🔑 PURPOSE

Provide a **fast, consistent method** for evaluating student work using:

* Technical competencies (HTML, CSS, JS, Debugging, Structure)
* Core Abilities (Collaboration, Professionalism, etc.)

---

# 🧱 1. SCORING SCALE (USE CONSISTENTLY)

| Score                     | Meaning                       | Instructor Heuristic                                 |
| ------------------------- | ----------------------------- | ---------------------------------------------------- |
| **4 — Exceeds**           | Correct + intentional + clean | “This works well and shows clear understanding”      |
| **3 — Meets**             | Works with minor issues       | “This is acceptable and functional”                  |
| **2 — Developing**        | Partial / inconsistent        | “They tried, but gaps are visible”                   |
| **1 — Needs Improvement** | Broken / unclear              | “This does not work or is missing key understanding” |
| **0**                     | Missing                       | “No submission or non-functional”                    |

---

# 🧱 2. TECHNICAL SCORING (PRIMARY)

Score quickly based on **what you observe**, not perfection.

### 🔹 Structure (HTML)

* Is content logically organized?
* Are semantic elements used?

👉 If it “makes sense and works” → **3**
👉 If it’s clean and intentional → **4**

---

### 🔹 Styling & Layout (CSS)

* Is layout readable and consistent?
* Does spacing/structure feel intentional?

👉 If usable → **3**
👉 If polished and consistent → **4**

---

### 🔹 Interactivity (JavaScript)

* Does it work?
* Does behavior match intent?

👉 Works → **3**
👉 Clean + correct + intentional → **4**

---

### 🔹 Debugging & Problem Solving

* Can they fix issues?
* Do they use tools (console, DevTools)?

👉 Fixes most issues → **3**
👉 Explains + systematic → **4**

---

### 🔹 Structured Development

* Is code organized?
* Are functions used appropriately?

👉 Understandable → **3**
👉 Clean, reusable, intentional → **4**

---

# 🧱 3. CORE ABILITIES (SECONDARY — OBSERVE, DON’T OVERGRADE)

---

### 🔹 Solve Problems

* Do they recover from issues?

👉 Independent → **4**
👉 Needs help → **2–3**

---

### 🔹 Communicate Clearly

* Can they explain what they built?

👉 Clear explanation → **3–4**
👉 Struggles → **1–2**

---

### 🔹 Work Productively

* On task? Completed?

👉 Done on time → **3–4**
👉 Incomplete → **1–2**

---

### 🔹 Value Learning

* Uses resources? AI appropriately?

👉 Thoughtful use → **3–4**
👉 Minimal effort → **1–2**

---

### 🔹 Work Cooperatively (Pair Programming)

* Engaged with partner?
* Shared roles?

👉 Active collaboration → **3–4**
👉 Passive → **1–2**

---

### 🔹 Act Professionally (Remote Expectations)

* Camera on, engaged, respectful?
* Participates in discussion?

👉 Consistent presence → **3–4**
👉 Disengaged → **1–2**

---

# 🧱 4. FAST SCORING WORKFLOW (USE EVERY TIME)

### Step 1 — Scan (10–20 seconds)

* Does it work?
* Is it complete?

---

### Step 2 — Score Technical (60–90 seconds)

* Assign 3 by default if functional
* Move to:

  * **4** if clean/intentional
  * **2** if inconsistent

---

### Step 3 — Score Core Abilities (30–60 seconds)

* Based on:

  * lab observation
  * interaction
  * submission quality

---

### Step 4 — Comment ONLY if needed

Use comments when:

* score is 1 or 2
* major misunderstanding
* exceptional work (optional)

---

# 🧱 5. EMPHASIS BY COURSE PHASE

| Phase       | Focus                       |
| ----------- | --------------------------- |
| Weeks 1–3   | Structure + CSS             |
| Weeks 4–7   | JavaScript + Debugging      |
| Weeks 8–11  | Systems (Data, State)       |
| Weeks 12–15 | Quality (Performance, UX)   |
| Weeks 16–17 | Integration + Communication |

---

# 🧱 6. COMMON PITFALLS (AVOID)

❌ Grading perfection instead of functionality
❌ Over-commenting (slows workflow)
❌ Ignoring Core Abilities
❌ Scoring inconsistently between students
❌ Letting one mistake dominate all categories

---

# 🔑 FINAL PRINCIPLE

> **Score what is observable, not what you assume.
> Reward working systems, not perfect code.**

---

# 🧭 ONE-LINE SUMMARY

> “If it works → 3.
> If it works well and shows intention → 4.
> If it struggles → 2.
> If it fails → 1.”
