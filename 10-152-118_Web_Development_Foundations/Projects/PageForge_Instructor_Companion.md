# **PageForge — Instructor Companion Project Framework**

---

## **Purpose**

`PageForge` is the **instructor demonstration project** for this course.

Students will choose their own project track from the project guide.

The instructor will build `PageForge` alongside the course as a **reference example** that demonstrates how the weekly concepts, assignments, and iterative development process can be applied to one evolving project over time.

---

## **What PageForge Is**

`PageForge` is a browser-based application that allows a user to assemble a simple webpage from reusable content blocks.

The project is intentionally constrained.

It is **not** a full no-code website builder.

It is a structured demonstration project used to model:

* HTML structure
* CSS styling and layout
* JavaScript interactivity
* iterative development
* refinement over time
* system thinking

---

## **What PageForge Is Not**

To keep the project aligned to the course and avoid unnecessary complexity, `PageForge` should **not** be treated as:

* a required student project
* a pixel-perfect design tool
* a full drag-anywhere page editor
* a full website hosting platform
* a replacement for student project choice

The purpose is to provide a stable instructional example, not to build a production-grade tool.

---

## **Relationship to Student Projects**

Students:

* choose a project track from the approved guide
* build their own project iteratively across the course
* apply weekly concepts to their chosen domain

Instructor:

* builds `PageForge` as a parallel example
* uses the same weekly rhythm as students
* demonstrates how one project grows through structured iteration
* models refinement, debugging, organization, and decision-making

This preserves student ownership while still giving the class a common reference point.

---

## **Instructional Role**

`PageForge` should serve as:

* a **demo project**
* a **reference implementation**
* a **teaching model for iteration**
* a **bridge between weekly concepts and applied development**

It should help students see:

* how a project begins simply
* how features are added in small steps
* how structure supports growth
* how refinement is part of development

---

## **Recommended Scope**

The minimum viable version of `PageForge` should remain focused on a small set of understandable features.

Recommended core features:

* a small multi-page site structure for the app itself
* a block list or block selector
* the ability to add predefined content blocks
* the ability to edit block content
* the ability to remove or reorder blocks
* a live preview area
* limited style customization
* export of generated HTML/CSS at a simple level

Recommended constraints:

* use predefined block types
* use limited design controls
* avoid freeform drag-anywhere editing in the early version
* avoid unnecessary abstraction too early
* keep the interface understandable for beginning students

---

## **Suggested Block Types**

The project can remain manageable by limiting block types to a small, reusable set such as:

* Hero section
* Text section
* Image section
* Card grid
* Call-to-action section
* Footer

These are enough to demonstrate structure, layout, content management, and interactivity without overwhelming the instructional flow.

---

## **Alignment to Course Structure**

`PageForge` should follow the same development philosophy used in the course artifacts:

* build something real
* start simple
* improve it over time
* refine rather than restart
* connect new concepts to existing work

This makes the project a demonstration of process, not just product.

## **Week-by-Week Alignment (Recommended)**

### **Week 1 — Structure**

Build the base multi-page HTML structure for `PageForge`.

Examples:

* Home page
* Builder page
* About or Help page

Focus:

* semantic structure
* navigation
* clear organization

---

### **Week 2 — Styling**

Add foundational CSS styling.

Examples:

* typography
* color system
* spacing
* basic visual hierarchy

Focus:

* readability
* consistency
* clear separation between structure and appearance

---

### **Week 3 — Layout**

Improve layout and responsiveness.

Examples:

* sidebar area
* control panel
* preview panel
* stacked mobile layout

Focus:

* layout thinking
* responsive behavior
* visual organization

---

### **Week 4 — JavaScript Foundations**

Introduce the project data and logic in manageable ways.

Examples:

* arrays of block types
* objects representing block content
* simple conditional logic

Focus:

* data structure thinking
* logic before complexity

---

### **Week 5 — DOM Interaction**

Connect JavaScript to the interface.

Examples:

* add a block
* remove a block
* update displayed content

Focus:

* event handling
* DOM updates
* visible response

---

### **Week 6 — Debugging**

Use the project to model investigation and repair.

Examples:

* broken selectors
* incorrect rendering
* event issues

Focus:

* process over guessing
* understanding how to diagnose issues

---

### **Week 7 — Structured JavaScript**

Refactor for clarity.

Examples:

* separate render logic
* separate event handling
* separate data updates

Focus:

* readability
* maintainability
* clear function purpose

---

### **Week 8 — Data Structures**

Strengthen how block data is organized.

Examples:

* arrays of blocks
* objects with properties
* using data to drive the preview

Focus:

* organized information
* structure that supports growth

---

### **Week 9 — Forms and Input**

Capture user input to modify blocks.

Examples:

* edit title text
* update descriptions
* choose style options

Focus:

* form handling
* input to state
* user-controlled behavior

---

### **Week 10 — Data and JSON**

Introduce external or structured data.

Examples:

* load block presets from JSON
* load starter themes from JSON

Focus:

* request -> receive -> use
* data-driven interface behavior

---

### **Week 11 — Integration**

Show how the pieces work together as a system.

Examples:

* input updates data
* data updates preview
* preview supports export

Focus:

* flow
* system thinking
* connected behavior

---

### **Week 12 — Efficiency and Stabilization**

Improve how the system behaves.

Examples:

* reduce repeated rendering
* simplify update logic
* remove redundancy

Focus:

* intentional updates
* cleaner logic
* stable behavior

---

### **Week 13 — Reliability**

Make the project safer and more predictable.

Examples:

* validate empty input
* handle missing values
* use fallback content

Focus:

* defensive thinking
* reliability
* graceful failure

---

### **Week 14 — UX and Refinement**

Improve how the application feels to use.

Examples:

* clearer labels
* better layout feedback
* more understandable controls

Focus:

* usability
* consistency
* clarity

---

### **Week 15 — Final Polish**

Prepare the project as a complete demonstration of course growth.

Examples:

* cleaner interface
* stronger preview experience
* more polished export output

Focus:

* presentation
* completeness
* visible improvement over time

---

## **Important Instructional Reminder**

Students should not be expected to reproduce `PageForge` exactly.

Instead, they should use it as a model for:

* how to build iteratively
* how to connect new concepts to existing work
* how to improve a system over time

The class should understand:

> `PageForge` is the instructor's example project.
> Your project track is your own version of iterative development.

---

## **Suggested Instructor Framing**

You may explain it this way:

> “You will choose your own project track for the course.
> I will build a project called `PageForge` alongside you.
> It is not the required project for the class.
> It is the example project I will use to show how each week's concepts can be applied, improved, and refined over time.”

---

## **Final Note**

The purpose of `PageForge` is not to demonstrate complexity.

Its purpose is to demonstrate **process**.

If students can see how a project grows from simple structure into a working interactive system, then `PageForge` is doing its job.
