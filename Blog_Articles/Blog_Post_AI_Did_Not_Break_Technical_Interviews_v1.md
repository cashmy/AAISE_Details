# AI Didn't Break Technical Interviews. It Exposed the Broken Ones.

## The Interview That Time Forgot

There is a particular kind of technical interview that refuses to die.

The candidate is placed in front of a coding problem, often under artificial
time pressure, and asked to produce a solution from memory. The problem may
involve array manipulation, string parsing, recursion, sorting, searching,
graph traversal, or some other familiar technical pattern. Sometimes the
candidate is asked to write code without documentation, without an editor,
without internet access, and now, very often, without AI.

When candidates use AI anyway, some companies react with surprise or outrage.
They call it cheating. They tighten the rules. They add surveillance. They
design more restrictive interview environments. They try to preserve the old
test by preventing access to the new tool.

But I think that reaction misses the deeper issue.

AI did not break technical interviews.

It exposed the broken ones.

The problem is not merely that candidates now have access to AI. The problem is
that many technical interviews were already measuring a narrow and often
misleading version of programming ability. AI simply made that mismatch harder
to ignore.

## The Old Test Was Already Weak

The traditional logic-memory interview rests on a questionable assumption: that
the ability to reproduce a solution pattern under artificial conditions is a
strong proxy for real software development ability.

Sometimes it is. But often it is not.

A person who can memorize common interview patterns may perform well in that
environment without being especially strong at building, debugging,
integrating, maintaining, or explaining real systems. Likewise, a capable
developer may struggle to recall the exact shape of a particular algorithm
under pressure while still being excellent at problem framing, code
comprehension, validation, and practical engineering.

That was true before AI.

Good assessment design has never been about asking whether someone can
regurgitate a pattern in the most constrained possible environment. Good
assessment design asks whether the task being measured actually reflects the
competence being claimed.

If the competence is "can this person perform memorized coding drills under
pressure," then a closed-book puzzle interview may be appropriate.

But if the competence is "can this person function as a useful software
developer," then the assessment needs to measure something broader and more
authentic.

## Programming Is Not Just Logic Recall

Real programming work is not primarily a memory sport.

It includes memory, certainly. Developers need working fluency with language
syntax, data structures, control flow, APIs, and common patterns. But that is
only part of the work.

Actual software development also requires:

- understanding the problem
- identifying inputs, outputs, and constraints
- selecting an appropriate approach
- recognizing when an approach is too complex or too fragile
- reading existing code
- debugging unexpected behavior
- testing assumptions
- validating edge cases
- communicating tradeoffs
- adapting when requirements shift
- using tools responsibly
- knowing when a solution is good enough and when it is dangerous

Those are not secondary skills.

They are the work.

The trouble with many technical interviews is that they collapse this broader
work into one narrow performance: can the candidate produce the expected logic
shape quickly, from memory, under pressure?

That tells us something. It does not tell us enough.

## AI Changed the Environment, Not the Principle

AI-assisted development changes the practical environment in which developers
work.

A developer can now ask an AI tool to draft a function, explain unfamiliar code,
suggest a test case, identify a bug, compare two approaches, or refactor a
messy block into something more readable. That does not mean the developer no
longer needs skill. It means the center of skill is moving.

The durable skill is less about instinctively recalling every implementation
pattern and more about governing the development process:

- Can you frame the problem clearly?
- Can you recognize the relevant concept?
- Can you tell whether the generated code fits?
- Can you detect when AI misunderstood the requirement?
- Can you test the result?
- Can you explain what changed?
- Can you make a responsible modification when the requirement shifts?

If a candidate uses AI to bypass all thinking, that is a problem.

But if a candidate uses AI as a normal professional tool, inspects the output,
corrects it, validates it, and explains the decisions, that may be a stronger
signal than a memorized whiteboard solution.

The distinction matters.

Hidden substitution is not the same as accountable tool use.

## Cheating or Misaligned Assessment?

Companies often frame AI use during interviews as cheating. Sometimes that is
accurate. If the rules forbid AI and a candidate secretly uses it, there is an
integrity problem.

But there is another possibility companies should be willing to consider:

Maybe the test is misaligned with the real work.

If your assessment becomes meaningless the moment a candidate has access to the
same kind of tool they will use on the job, then the assessment may not be
measuring durable job performance. It may be measuring tool deprivation.

That is a fragile basis for hiring.

Imagine testing a professional accountant by forbidding spreadsheets. Imagine
testing a network engineer by forbidding documentation. Imagine testing a
software developer by forbidding the tools that increasingly shape actual
software work, then concluding that the person who uses those tools well is the
problem.

The issue is not that every interview should become open-ended and tool-free in
the opposite direction. Constraints still matter. Independent reasoning still
matters. Integrity still matters.

But if the only way an assessment works is by pretending modern tools do not
exist, the assessment deserves scrutiny.

## The Pedagogical Mistake

There is also a pedagogical problem underneath this.

In education, a good test should align with the intended learning outcome. If
you want to know whether a student understands a concept, you do not only ask
them to reproduce a memorized example. You ask them to apply the concept,
explain it, adapt it, debug it, or distinguish it from a similar but incorrect
approach.

The same principle applies to technical hiring.

If the job requires real development ability, then the interview should test
development ability in a way that resembles the work closely enough to produce
useful evidence.

A memory-first coding puzzle may be efficient. It may be familiar. It may be
easy to standardize. But efficiency and familiarity are not the same as
validity.

An interview can be difficult and still poorly designed.

An interview can filter candidates and still filter for the wrong things.

An interview can feel rigorous while mostly rewarding prior exposure to the
interview genre.

That is the uncomfortable part. Some companies have mistaken ritualized
difficulty for meaningful assessment.

## What AI Makes Visible

AI makes the weakness visible because it attacks the part of the interview that
was easiest to mistake for skill: fast production of plausible code.

If the task is simply "produce the code," AI can often help. Sometimes it can
help too much for the old interview model to survive unchanged.

But that should tell us something.

If AI can complete the task, then the human assessment should move upward.

The question should become:

- Why is this the right approach?
- What assumptions does this solution make?
- What edge cases might fail?
- What would you test first?
- What is the complexity tradeoff?
- What would you simplify for production?
- What would you change if the input grew tenfold?
- What part of the AI output do you distrust?
- What would you reject, rewrite, or verify?

Those questions are harder to fake because they test judgment, not only output.

They also resemble real work more closely.

## A Better Technical Interview

A better interview model does not have to be soft.

In fact, it can be more demanding than the old model because it asks candidates
to demonstrate deeper ownership.

For example, a company could give a candidate a realistic problem and allow
normal tools, including AI, under explicit rules. The candidate might be asked
to:

- restate the problem and constraints
- create or critique a solution
- use AI only in disclosed ways
- explain what AI contributed
- identify what they changed or rejected
- write or select useful tests
- debug a failing case
- discuss tradeoffs
- modify the solution when a requirement changes

That kind of interview tests the thing companies actually need to know:

Can this person govern technical work?

Not merely:

Can this person reproduce a known pattern from memory?

There is still room for manual work. There is still room for asking a candidate
to write code without AI. But that should be done intentionally, to test a
specific foundational skill, not as the default definition of competence.

## The New Signal

The strongest candidates in an AI-shaped development environment will not
necessarily be the ones who memorize the most patterns.

They will be the ones who can think clearly with tools.

They will know how to frame a problem before asking for output. They will know
how to interrogate generated code. They will know how to test and validate.
They will know when AI has produced something plausible but wrong. They will be
able to explain their choices. They will understand that assistance does not
remove responsibility.

That is not cheating.

That is modern technical competence.

The weak candidate is not the one who uses AI. The weak candidate is the one
who cannot explain, validate, or govern what AI produced.

## What Companies Should Stop Doing

Companies should stop treating every use of AI as evidence of dishonesty while
continuing to use interview designs that were already misaligned with real
development work.

They should stop confusing tool restriction with rigor.

They should stop assuming that logic memory is the same thing as engineering
judgment.

They should stop complaining that candidates are adapting to the actual tool
environment while the interview remains frozen in an older one.

Most importantly, they should stop using assessments that collapse the human
role into code production alone.

That is precisely the layer AI is compressing.

## What Companies Should Measure Instead

Companies should measure whether candidates can:

- understand and clarify ambiguous requirements
- select a reasonable approach
- recognize relevant concepts
- read and critique code
- use tools transparently
- test behavior
- debug failures
- explain tradeoffs
- adapt to new constraints
- preserve ownership of the final result

That does not lower the bar.

It moves the bar to where the work actually is.

## The Real Lesson

AI did not make technical assessment impossible.

It made weak assessment harder to defend.

If an interview only works when candidates are isolated from modern tools, then
the interview may be testing a historical work condition more than a current
professional capability.

The real question is not whether candidates can be forced back into the old
environment long enough to complete a puzzle.

The real question is whether they can operate responsibly in the environment
they will actually work in.

That environment includes AI.

So the better technical interview is not one that pretends AI does not exist.

It is one that reveals whether the candidate can use AI without surrendering
thought, judgment, or responsibility.

That is the new signal.

And honestly, it was the signal we should have been looking for all along.
